网络请求与数据展示：让 App 接上真实世界

前七章的 App 都是"自给自足"的：数据要么写死，要么存在本地。 这一章把数据换成真实接口，同时解决随之而来的一整套问题： 加载中该显示什么、失败了怎么告诉用户、分页怎么不重复请求、页面离开时未完成的请求怎么办。 学完这一章，你就具备了把任何后端接口接进 App 的能力。

8.1

先建立思维：请求一定有"三种结局"

15 分钟 · 讲授

前端请求后端，本质是一次"发出去 → 等一会儿 → 拿回结果"的异步过程。 新手写请求时只想着"成功怎么办"，于是代码就长成这样：把 success 回调写得很完整， fail 完全不管。结果一断网，用户看到的就是一个永远转圈的空白页面。

任何一次请求都只有三种结局，界面也必须准备好三种状态：

结局技术上是什么界面必须表现
① 加载中 请求已发出，结果还没回来 骨架屏或 loading 提示（不要留白，用户会以为卡死）
② 成功但有数据 / 成功但空 success 回调，statusCode 正常 渲染列表；如果数组为空，要显示空态文案（第 4 章强调过）
③ 失败 fail 回调（网络断了、超时），或业务码表示出错 明确的错误提示 + 重试入口
ⓘ
一个容易被忽略的区分：HTTP 状态码 ≠ 业务状态码

statusCode 是 HTTP 层的（200 表示"服务器正常回复了"）， 但服务器可能在 200 的响应体里告诉你"{"code": 401, "msg": "登录已过期"}"。 所以判断成功要两层都看：先看 statusCode 是否在 2xx， 再看业务字段（通常叫 code / errCode / success）。 只判断其中一层，都会出现"命令式成功、结果什么也没显示"的诡异情况。

8.2

uni.request：参数怎么传，返回里有什么

25 分钟 · 讲授

uni.request 的用法和浏览器的 fetch 思路一样，但它是跨端统一的： 在 App、Web、小程序里写法完全相同。

pages/demo/request.uvue —— 最常用的两种请求 
<script setup>
  // ① GET：参数用 data 传，会自动拼到 url 后面
  const loadList = () => {
    uni.request({
      'url': 'https://api.example.com/notices',
      'method': 'GET',
      'data': { 'page': 1, 'size': 10 },
      'timeout': 8000,                        // 默认 60000ms，建议显式设短一点
      'success': (res) => {
        // res.statusCode 是 HTTP 状态码
        if (res.statusCode == 200) {
          // res.data 默认已经做过一次 JSON.parse（dataType 默认就是 'json'）
          console.log('返回数据：', res.data)
        }
      },
      'fail': (err) => {
        // 网络层失败：超时、断网、地址不合法等
        console.log('请求失败：', err.errCode, err.errMsg)
      },
      'complete': () => {
        // 成功或失败都会走这里，适合关闭 loading
        console.log('请求结束')
      }
    })
  }

  // ② POST：data 放在请求体里
  const submitForm = () => {
    uni.request({
      'url': 'https://api.example.com/signup',
      'method': 'POST',
      'header': { 'Content-Type': 'application/json' },
      'data': { 'name': '汽水同学', 'phone': '13800001111' },
      'success': (res) => {
        console.log('提交结果：', res.statusCode, res.data)
      }
    })
  }
</script>

参数速查表（按重要性排序）

参数默认值说明与坑
url必填接口地址，建议写完整地址（http/https）
method"GET"合法值：GET / POST / PUT / PATCH / DELETE / HEAD / OPTIONS
datanull App-Android 端只支持 UTSJSONObject 或 string 类型—— 传数组、数字等基本类型可能报"data 参数类型不合法"（errCode 600008）。
Android 4.51+ / iOS 4.61+ 起支持 ArrayBuffer（传二进制）
headernull类型是 UTSJSONObject；header 里不能设置 Referer
timeout60000单位毫秒。移动网络建议 8000–15000，太长用户会以为卡死
dataType"json" 设为 json 时框架会对返回数据做一次 JSON.parse，所以 res.data 通常已经是对象； 返回的不是合法 JSON 时会失败（errCode 100001），此时可改成非 json
responseType—设置响应数据类型（需要拿二进制时用）
sslVerify—是否验证 SSL 证书。自签证书的测试环境才需要动它，生产环境不要关
withCredentials—跨域请求是否携带 cookies
firstIpv4falseDNS 解析优先使用 IPv4；某些网络环境下能缓解连接慢
enableQuic / enableChunkedfalse协议层优化与分块传输，属于进阶项（Android 5.23+ 默认开启 Brotli 压缩）
💡
成功回调里能拿到什么（RequestSuccess）：

data（服务器返回的数据，已按 dataType 处理）、 statusCode（HTTP 状态码）、header（响应头）、cookies（字符串数组）。 调试时最简单有效的做法是：先把整个 res 打印出来（JSON.stringify(res.data)）， 确认字段结构之后再写渲染代码——第 4 章说过，接口结构与假设不一致是渲染报错的头号原因。

8.3

失败处理：错误码、重试与取消请求

20 分钟 · 讲授

官方给 fail 回调提供了明确的错误码，用它可以给出"人话"提示，而不是把英文错误甩给用户。

errCode含义建议的界面表现
5接口超时"网络较慢，请重试" + 重试按钮
600003网络中断"当前无网络连接，请检查网络"（可配合网络状态监听）
600009URL 格式不合法开发期问题：检查 url 拼写与协议头
600008data 参数类型不合法开发期问题：App-Android 端请传对象或字符串
100001json 数据解析错误服务器返回的不是合法 JSON；确认 dataType 与接口格式
1000服务端系统错误"服务暂时不可用，请稍后再试"
602001request 系统错误记录日志，提供重试
600010Cronet 模块加载失败多为运行环境问题，重试或重启基座
把错误码翻译成人话 + 取消未完成的请求 
<script setup>
  // ① 错误码 → 用户能看懂的提示
  const friendlyError = (code: number): string => {
    if (code == 5) return '网络较慢，加载超时，请重试'
    if (code == 600003) return '当前无网络连接，请检查网络设置'
    if (code == 1000) return '服务暂时不可用，请稍后再试'
    if (code == 100001) return '数据格式异常，请联系管理员'
    return '加载失败，请稍后重试'
  }

  // ② 请求任务与取消：uni.request 会返回一个 RequestTask
  let task: RequestTask | null = null

  const load = () => {
    task = uni.request({
      'url': 'https://api.example.com/notices',
      'timeout': 8000,
      'success': (res) => {
        if (res.statusCode != 200) {
          uni.showToast({ 'title': '服务异常（' + res.statusCode + '）', 'icon': 'none' })
          return
        }
        // 业务码也要判断
        console.log('数据：', res.data)
      },
      'fail': (err) => {
        uni.showToast({ 'title': friendlyError(err.errCode), 'icon': 'none' })
      }
    })
  }

  // ③ 页面离开时取消未完成的请求，避免"回来还在跑"与回调里访问已销毁页面
  onUnload(() => {
    if (task != null) {
      task.abort()                    // 中断网络请求
      task = null
    }
  })
</script>
ⓘ
RequestTask 还能做什么？

除了 abort() 取消请求，它还支持 onHeadersReceived（监听响应头，可用于读取 token、判断是否需要刷新登录态） 与 onChunkReceived（监听分块数据，做流式输出）。 这两个能力从 HBuilderX 4.71 起支持，属于进阶用法。

!
三个平台相关的注意点：

① 小程序端必须配置合法域名（在对应平台后台把 request / uploadFile / downloadFile 的域名加入白名单）， 否则请求会被直接拦截；App 端一般不受此限制，但请使用 HTTPS 并保持 sslVerify 开启； ② App-Android 的 data 只支持对象或字符串（见 8.2 表格）； ③ 不要在前端代码里硬编码密钥（AppSecret、数据库密码之类）—— 客户端代码是可以被反编译的，敏感操作必须由服务端完成。

8.4

封装：把"每次都要写的东西"收进一个文件

25 分钟 · 讲授 + 演练

如果每个页面都直接写一遍 uni.request，你会发现这些东西在重复： 域名前缀、超时时间、token 请求头、错误提示、statusCode 判断、loading 开关。 正确做法是抽成一个请求工具，页面里只写"请求哪个接口、拿到什么数据"。

✕
先看"不封装"的代价：

某天要把接口域名从测试环境换到生产环境——你需要在 20 个页面里各改一次 url； 某天要加一个 token 请求头——又是 20 处。 而封装之后，这些都只改一个文件。这也是"能用"和"能维护"的分界线。

utils/request.ts —— 一个够用的请求封装 
// 统一配置：换环境只改这一行
const BASE_URL = 'https://api.example.com'

type RequestOptions = {
  url: string,
  method?: string,
  data?: UTSJSONObject | null,        // 注意 App-Android 只支持对象或字符串
  showError?: boolean                 // 是否自动弹错误提示
}

// 把回调式 API 包装成"能 await"的形式，页面里写起来更顺
export const request = <T>(options: RequestOptions): Promise<T | null> => {
  return new Promise<T | null>((resolve) => {
    uni.request({
      'url': BASE_URL + options.url,
      'method': options.method ?? 'GET',
      'data': options.data ?? null,
      'timeout': 10000,
      'header': {
        'Content-Type': 'application/json',
        // 登录后把 token 放进请求头（实际 token 从本地存储读，第 9 章）
        'Authorization': 'Bearer ' + (uni.getStorageSync('token') ?? '')
      },
      'success': (res) => {
        // 第一层：HTTP 状态码
        if (res.statusCode != 200) {
          if (options.showError !== false) {
            uni.showToast({ 'title': '服务异常（' + res.statusCode + '）', 'icon': 'none' })
          }
          resolve(null)
          return
        }
        // 第二层：业务码（这里假设后端返回 { code, data, msg }）
        const body = res.data as UTSJSONObject
        const code = body['code'] as number
        if (code != 0) {
          if (options.showError !== false) {
            uni.showToast({ 'title': (body['msg'] as string) ?? '请求失败', 'icon': 'none' })
          }
          resolve(null)
          return
        }
        resolve(body['data'] as T)
      },
      'fail': (err) => {
        if (options.showError !== false) {
          uni.showToast({ 'title': friendlyError(err.errCode), 'icon': 'none' })
        }
        resolve(null)
      }
    })
  })
}

// 页面里调用：只关心"要什么数据"
// const list = await request<Notice[]>({ url: '/notices', data: { page: 1 } })
💡
封装时值得留意的四件事：

① 统一错误提示，但留一个开关（showError: false）—— 有些请求失败不需要打扰用户（例如后台静默刷新）； ② 返回 null 而不是抛异常——页面里用 if (data != null) 判断即可，逻辑更平； ③ 把 token 从存储里读，不要硬编码，并留好"token 失效统一跳登录"的位置； ④ 官方 request 示例里还演示了 请求拦截器的用法（统一加 header、统一打日志）， 需要更"框架化"的做法时可以对照官方示例实现。

8.5

实战：一个真正的分页列表页

30 分钟 · 全程动手

把第 7 章的下拉刷新 / 触底加载骨架，换成真实请求，并把三态补齐。 这是移动端最高频的页面形态，写熟一次，后面每个列表页都能套。

pages/notice/list.uvue 
<template>
  <view class="page">
    <!-- ① 加载中：首次加载显示骨架，避免白屏 -->
    <view v-if="loading && list.length == 0" class="tip-box">
      <text class="tip-text">正在加载…</text>
    </view>

    <!-- ② 失败：给错误原因 + 重试按钮（不是只提示一下） -->
    <view v-else-if="error.length > 0 && list.length == 0" class="tip-box">
      <text class="tip-text">{{ error }}</text>
      <button size="mini" class="retry" @click="reload">重新加载</button>
    </view>

    <!-- ③ 空态：真实用户最常遇到的界面 -->
    <view v-else-if="list.length == 0" class="tip-box">
      <text class="tip-text">还没有通知</text>
    </view>

    <!-- ④ 正常数据 -->
    <view v-else>
      <view v-for="item in list" :key="item.id" class="item">
        <text class="item-title">{{ item.title }}</text>
        <text class="item-time">{{ item.time }}</text>
      </view>

      <!-- 底部状态：三种文案都要有 -->
      <view class="footer-tip">
        <text class="tip-text">{{ loading ? '加载中…' : (noMore ? '没有更多了' : '上拉加载更多') }}</text>
      </view>
    </view>
  </view>
</template>
<script setup>
  import { request } from '@/utils/request'

  type Notice = { id: number, title: string, time: string }

  const list = ref<Notice[]>([])
  const page = ref<number>(1)
  const loading = ref(false)
  const noMore = ref(false)
  const error = ref<string>('')

  const loadPage = (p: number): Promise<void> => {
    return new Promise((done) => {
      // 演示：这里换成真实的 request 调用
      // request<Notice[]>({ url: '/notices', data: { page: p, size: 10 } }).then((rows) => {
      //   if (rows == null) { error.value = '加载失败，请重试'; done(); return }
      //   list.value = p == 1 ? rows : list.value.concat(rows)
      //   noMore.value = rows.length < 10
      //   done()
      // })
      setTimeout(() => {
        const rows: Notice[] = []
        for (let i = 0; i < 10; i++) {
          const id = (p - 1) * 10 + i + 1
          rows.push({ 'id': id, 'title': '校园通知 ' + id, 'time': '2026-10-11' })
        }
        list.value = p == 1 ? rows : list.value.concat(rows)
        noMore.value = p >= 3
        done()
      }, 400)
    })
  }

  const reload = async () => {
    if (loading.value) return
    loading.value = true
    error.value = ''
    page.value = 1
    noMore.value = false
    await loadPage(1)
    loading.value = false
  }

  // 下拉刷新
  onPullDownRefresh(async () => {
    await reload()
    uni.stopPullDownRefresh()        // 别忘了停止刷新动画
  })

  // 触底加载：必须加锁，否则会重复请求
  onReachBottom(async () => {
    if (loading.value || noMore.value) return
    loading.value = true
    const next = page.value + 1
    await loadPage(next)
    page.value = next
    loading.value = false
  })

  // 每次显示都重新加载：保证从详情页返回时数据是最新的（第 7 章）
  onPageShow(() => {
    if (list.value.length == 0) reload()
  })
</script>

!
分页最容易出的三个问题：

① 重复请求：触底会连续触发，必须用 loading 锁 + noMore 标记； ② 页码错乱：请求是异步的，如果不等结果回来就 page + 1，会出现跳页； 正确做法是拿到结果再推进页码（示例中的写法）； ③ 数据拼接错误：第一页要"替换"、后续页要"追加"（concat），写成一样就会只看到最后一页。

8.6

上传、下载与网络状态

15 分钟 · 讲授

官方网络模块除了 request，还有一套配套能力，做"发布二手商品""下载文件""断网提示"时都会用到。

API用途关键点
uni.uploadFile 上传文件（图片、音频等） 通常先用 uni.chooseImage 拿到本地路径，再上传；比 request 多一个 name（表单字段名）与 filePath
uni.downloadFile 下载文件到本地 拿到临时路径后可用 uni.saveFile / uni.openDocument 处理
uni.getNetworkType 获取当前网络类型 返回 wifi / 4g / 5g / none 等，可用于"仅在 WiFi 下下载"
uni.onNetworkStatusChange 监听网络状态变化 断网时给出离线提示，恢复后自动重试，体验提升明显
uni.connectSocket / connectEventSource WebSocket 与服务端推送 做聊天、实时通知时用；课程项目里一般为加分项
图片上传 + 断网监听（各 10 行左右） 
<script setup>
  const uploadAvatar = () => {
    // 第一步：选择图片，拿到本地临时路径
    uni.chooseImage({
      'count': 1,
      'success': (res) => {
        const filePath = res.tempFilePaths[0]

        // 第二步：上传
        uni.uploadFile({
          'url': BASE_URL + '/upload',
          'filePath': filePath,
          'name': 'file',                        // 后端接收的字段名
          'formData': { 'type': 'avatar' },      // 附加表单字段
          'header': { 'Authorization': 'Bearer ' + token },
          'success': (up) => {
            console.log('上传返回：', up.statusCode, up.data)
          },
          'fail': (err) => {
            uni.showToast({ 'title': '上传失败', 'icon': 'none' })
          }
        })
      }
    })
  }
</script>
<script setup>
  const online = ref<boolean>(true)

  onLoad(() => {
    // 进入页面先查一次当前网络类型
    uni.getNetworkType({
      'success': (res) => {
        online.value = res.networkType != 'none'
      }
    })

    // 监听变化：断网提示、恢复自动重试
    uni.onNetworkStatusChange((res) => {
      online.value = res.isConnected
      if (!res.isConnected) {
        uni.showToast({ 'title': '网络已断开', 'icon': 'none' })
      } else {
        // 联网恢复后可以在这里自动重试上一次失败的请求
        console.log('网络已恢复：', res.networkType)
      }
    })
  })

  // 记得清理监听，避免重复注册（第 7 章的教训）
  onUnload(() => {
    uni.offNetworkStatusChange()
  })
</script>
ⓘ
关于"离线优先"的一个实用建议：

移动端的网络是"不可靠"的常态。一个成本很低但体验提升很大的做法是： 把上一次成功的列表数据缓存到本地（第 9 章的本地存储）， 下次进入页面先用缓存渲染，再去请求更新——用户就再也不会看到空白页。 这也是很多成熟 App 的做法。

调试与避坑：六个高频问题

15 分钟 · 讲授
现象原因解决
浏览器能请求，小程序请求被拒 小程序有域名白名单 到小程序后台把接口域名加入 request 合法域名（uploadFile / downloadFile 要分别加）
请求一直失败，errCode 600003 设备没网或接口域名不可达 用 getNetworkType 先判断；确认手机与服务器网络互通（内网地址在真机上通常访问不到）
请求很慢直到超时（errCode 5） 默认超时 60 秒，且后端未响应 显式设 timeout: 8000，并给用户"重试"入口
errCode 600008：data 参数类型不合法 App-Android 端 data 只支持对象或字符串 把参数包成对象：{ id: 3 }；不要直接传数字或数组
快速切换分类，列表显示的是上一次的结果 请求竞态：后发的请求先回来了 用"请求序号"或 abort()：只接受最后一次请求的结果
离开页面后回调还在执行、报错 未取消未完成的请求 在 onUnload 里 task.abort()，并在回调开头判断页面状态
解决"请求竞态"：只认最后一次请求 
<script setup>
  let seq = 0                     // 请求序号

  const search = async (keyword: string) => {
    seq = seq + 1
    const current = seq           // 记下本次请求的序号

    const data = await request<Notice[]>({ url: '/search', data: { 'kw': keyword } })

    // 回来时如果序号已经变了，说明有更新的请求发出，本次结果直接丢弃
    if (current != seq) {
      console.log('丢弃过期结果')
      return
    }
    list.value = data ?? []
  }
</script>

📌 今天你学到的，浓缩成 6 句话

任何请求都有加载中 / 成功（可能为空）/ 失败三种结局，界面必须三种都准备好； uni.request 的 method 默认 GET、timeout 默认 60000ms、 dataType 默认 json（会帮你做一次 JSON.parse）； App-Android 端的 data 只能是对象或字符串，header 里不能设 Referer； 判断成功要两层都看：statusCode 与业务码； fail 回调的 errCode 能翻译成人话（5 超时、600003 断网、1000 服务端错误、600008 参数类型错、100001 JSON 解析错）； 把重复的东西封进请求工具（域名、超时、token、错误提示、类型），页面只关心业务； 分页要加锁防重复、结果回来再推页码、首页替换后续追加， 并在 onUnload 里 abort() 取消未完成的请求。

三态思维 statusCode vs 业务码 uni.request dataType json App-Android data 限制 errCode 错误码 RequestTask.abort 请求封装 token 请求头 分页锁 空态与重试 请求竞态 uploadFile 网络状态监听

13.1

发布前的三道关：能跑通 → 像样 → 合规

10 分钟 · 讲授

很多同学卡在"打包"这一步，其实是因为把三件事混在一起做了。正确的顺序是逐关通过：

关要过什么验收方式常见失败
第一关
能跑通		 功能完整、真机可运行、无崩溃 在自己手机上把主流程走完 只在浏览器里测过，真机一片空白
第二关
像样		 图标、名称、启动界面、空态、深浅色、错误提示 给别人看 30 秒，他不问"这是半成品吗" 用默认图标、App 名叫 "uni-app"、启动白屏
第三关
合规		 隐私政策弹框、权限用途说明、不越界收集数据 装到干净手机上，第一次启动看到隐私弹框 同意前就初始化了统计/推送 SDK——会被应用市场打回
!
顺序很重要：先过第一关，再折腾打包。

打包本身是个"配置活"，一旦失败你很难判断是配置错了还是代码有 bug。 所以永远先用标准基座把功能跑通（第 1 章讲过：标准基座是官方预编译的运行环境，改代码即时生效、不用打包）， 确认没问题之后，再进入"配置图标 + 隐私 + 打包"的环节。

13.2

manifest.json：项目的身份证

25 分钟 · 讲授 + 演练

manifest.json 是 uni-app x 项目的配置文件，用来设置应用的名称、版本、图标等。 在 HBuilderX 中创建项目时，它保存在根目录。

配置项类型 / 默认值说明（官方口径）
appidstring由 DCloud 云端分配，不要自行修改
name / descriptionstring应用名称与描述（桌面图标下面显示的就是 name）
versionNamestring应用版本名称，给用户看的，例如 1.0.0
versionCodeinteger版本号，必须是整数，取值 1~2147483647；升级时必须高于上一次的值
uni-app-x 节点 object 必须存在——它是"这个项目是 uni-app x 项目"的核心标识。缺少它，HBuilderX 会把项目识别成 uni-app（js 引擎版），项目图标也会从圆形变方形
appobjectApp 平台通用配置（主题、隐私初始状态、发布配置）
app-android / app-ios / app-harmonyobject各平台专属配置（权限、最低版本、图标、启动界面等）
web / mp-weixinobjectWeb 与微信小程序平台配置

和这门课直接相关的几个开关

配置项（在 uni-app-x 下）默认值含义
vaporfalse是否启用蒸汽模式——我们整门课的主线就是它（第 1 章、附录 C）
styleIsolationVersion"2"样式隔离策略；蒸汽模式只支持 2.0（第 6 章）
flex-direction"column"uvue 页面默认的 flex 排列方向（第 2 章那个"默认竖排"的坑就是它）
vapor-render-target"bytecode"视图层编译目标，可取 bytecode 或 nativecode（第 1 章说"编译为机器码/字节码"，这里是它的开关）
配置项（在 app 下）默认值含义
defaultAppTheme"light"应用默认主题，可取 light / dark / auto（第 3 章暗黑模式的配置入口）
initPrivacyAuthorization"auto"隐私协议初始状态，可取 auto / agree / disagree（13.5 会用到）
distribute—发布配置：图标、启动界面、Android / iOS 专属发布项
💡
关于"内置模块"：uni-app x 走的是摇树，不是勾选。

老版 uni-app 需要在 manifest 里手动勾选内置模块；而官方说明： uni-app x 目前不提供内置模块选择，而是提供摇树机制自动选择内置模块—— 你用到了哪些能力，打包时就自动带上对应的模块，不用你操心。 这既是好事（少一类配置错误），也意味着不要照搬老教程里的"模块配置"步骤。

!
改完 manifest 一定要重新打包 / 重新运行。

图标、名称、权限、启动界面这些配置在打包后才生效，改了之后在标准基座里是看不到效果的， 很容易让人误以为"我配了没用"。判断方法：凡是与安装包有关的东西（图标、名称、启动图、权限）都必须重新打包。

13.3

图标与启动界面：被退审最多的两个坑

20 分钟 · 讲授
ⓘ
先知道一件事：uni-app x 默认没有启动界面。

官方说明：uni-app x 默认没有 splash 启动界面，因为打包后启动速度非常快； 你"可以自己做一个简单的 uvue 页面来当 splash"。 从 HBuilderX 3.99+ 起，官方开始支持配置 splash 启动界面（另有专门的启动界面配置文档）。 所以：没配启动图时看到短暂白屏是正常的，不必惊慌。

平台配置项尺寸要求硬性约束
Android
应用图标		 hdpi72 × 72 必须使用 png 格式
xhdpi96 × 96
xxhdpi144 × 144
xxxhdpi192 × 192
iOS
应用图标		 appstore1024 × 1024（iPhone/iPad） 必须 png，且图片中不能存在透明区域（有透明像素会被拒）
Android 启动界面建议分辨率
ldpi（~120dpi，不常见，通常可不配）240 × 320
mdpi（~160dpi，不常见）320 × 480
hdpi（~240dpi，不常见）480 × 800
xhdpi（~320dpi）720 × 1280
xxhdpi（~480dpi）1080 × 1920
xxxhdpi（~640dpi）2160 × 3840
ⓘ
Android 12 及以上还有一套新的启动界面规范。

官方为 Android 12 提供了专门的启动界面配置项（不配置就表示不适配 Android 12 启动界面）， 包含三部分：background（背景色，仅 Android 12 及以上生效，默认白色）、 icon（中部 Logo：xhdpi 480×480、xxhdpi 720×720、xxxhdpi 960×960）、 brand（底部品牌图：xhdpi 400×160、xxhdpi 600×240、xxxhdpi 800×320）。 这套配置在 Android 12 上是"系统统一启动画面"，比传统 splash 更规范。

💡
给不擅长设计的同学一份"最低可交付"方案：

① 图标：用纯色背景 + 一个字形/符号（例如课程表的日历、二手交易的"换"）， 先在 1024×1024 画布上做，然后导出四套 Android 尺寸与 iOS 的 1024； ② iOS 那版务必去掉透明通道（导出时取消 alpha，或铺一层背景色）； ③ 启动界面若懒得做，就用与应用主色一致的纯色背景 + 居中 Logo，比白屏专业得多。 ④ 命名建议：icon-72.png、icon-96.png…… 便于核对有没有漏。

!
还有一个容易被忽略的限制：manifest 里只能配置一个图标。

官方的提示是：App 端图片相关配置建议在 HBuilderX 的 manifest.json 可视化界面操作，不推荐手动改源码视图； 并且 manifest 中只能配置一个图标，如果要在应用发布后动态修改图标，需要用插件市场里的动态图标插件。 另外：图标与启动界面是"云打包后生效"的，在基座里预览不到。

13.4

Android 权限与版本适配：为什么会被市场退回

20 分钟 · 讲授
配置项默认值你要做什么
permissions空额外添加权限：项目真的用到、但框架没自动加上的权限写在这里
excludePermissions空强制移除权限：你完全没用到、但被打进包里的权限，建议移除——很多应用市场会因"申请了与功能无关的权限"退回
minSdkVersion21兼容的最低 Android 版本（API 等级）。注意：蒸汽模式官方要求最低 Android 6+（见附录 C）
targetSdkVersion32适配的目标 Android 版本。部分应用市场要求较高的 targetSdkVersion 才能提交审核——上架前务必确认目标市场的最低要求
abiFilters["arm64-v8a"]支持的 CPU 类型。默认只带 64 位；如需兼容很老的设备才考虑加 armeabi-v7a（代价是包体积变大）
enableResourceOptimizationstrue开启 Android 原生 res 资源优化，开启后 res 资源文件名会被混淆（对你有好处：难被逆向）
aaptOptions / buildFeatures / packagingOptions空留给需要深度定制的场景，课程项目一般用不到
ⓘ
需要原生的 AndroidManifest.xml / Info.plist？官方给了位置。

uni-app x 允许你在项目里放原生资源文件：Android 侧是 AndroidManifest.xml， iOS 侧是 Info.plist（官方各有一页文档说明）。 另外，manifestPlaceholders 不在 manifest.json 里配置—— 如果你的插件或三方 SDK 需要它，要写在项目的 nativeResources/android/manifestPlaceholders.json 文件里。

!
"权限最小化"是上架的第一原则。

应用市场审核会问：你申请这个权限干什么？ 本项目（课程表）只需要存储；二手交易需要相册/相机（选图）、可能还有网络状态。 不要因为"以后可能用得上"就留着通讯录、短信、通话记录这类权限—— 正确做法是：excludePermissions 清掉用不到的，真的需要时再加。 这与第 10 章的"用到时才申请"是同一条原则的两个层面。

13.5

隐私合规：一条红线与两种实现

25 分钟 · 讲授 + 演练

这一节的每句话都值得抄进你的项目文档里，因为它是"能不能上架"的分水岭。

✕
红线：用户同意隐私政策前，不要采集涉及隐私的数据。

官方的原话是："开发者需注意在用户同意隐私政策前，不要采集涉及隐私的数据。 如果违反当地法律或应用商店的要求，会无法上架应用商店甚至被处罚。" 所谓"采集"包括：初始化统计 SDK、上报设备标识（deviceId）、请求定位、读取相册等。 这也是最容易犯的错误——很多同学在 onLaunch 里直接初始化所有东西，就踩了线。

ⓘ
uni-app x 在这里有一个重要差异（很多人不知道）：

官方说明：uni-app 项目可以配置"原生隐私弹框"——因为开发者 js 执行较慢， 在原生代码获取隐私信息前可能来不及弹框，满足不了"先弹隐私政策、后采集数据"的合规要求； 但 uni-app x 项目是原生驱动执行的，开发者代码执行非常快，无需再提供隐私政策弹框配置，自行弹框即可。 换句话说：在 uni-app x 里，隐私弹框是你自己写的界面，而不是框架提供的一个配置项。 官方在 hello uni-app x 的 App.uvue 里给了基于 dialogPage 的示例代码 （搜索 uni.getPrivacySetting 就能找到）。

App.uvue —— 首次启动的隐私协议流程（官方示例思路） 
<script setup>
  // 官方示例在应用启动的 onLaunch 中判断隐私协议是否已被同意
  onLaunch(() => {
    checkPrivacy()
  })

  const checkPrivacy = () => {
    // 读取隐私协议状态（官方示例使用的 API）
    uni.getPrivacySetting({
      'success': (res) => {
        // 已经同意过：直接进入正常流程
        if (res.needAuthorization == false) {
          initAfterAgree()
          return
        }
        // 还没同意：弹出一个页面（官方示例用 dialogPage）展示隐私协议内容
        // 页面上有「同意」与「不同意」两个按钮，
        // 其中「同意」按钮使用 button 组件的 open-type="agreePrivacyAuthorization"
        openPrivacyDialog()
      }
    })
  }

  // ⚠ 关键：所有"涉及隐私"的初始化都必须放在用户同意之后
  const initAfterAgree = () => {
    // 例如：初始化统计 SDK、上报设备信息、请求定位、预读相册……
    console.log('用户已同意隐私政策，可以开始初始化')
  }
</script>

<!-- 隐私弹框页面里的同意按钮（button 组件的 open-type） -->
<template>
  <view class="privacy-page">
    <text class="privacy-title">用户隐私政策</text>
    <text class="privacy-body">{{ privacyText }}</text>
    <view class="privacy-actions">
      <!-- 不同意：退出应用或只提供基础功能 -->
      <button class="btn-no" @click="refuse">不同意</button>
      <!-- 同意：open-type 使用 agreePrivacyAuthorization -->
      <button class="btn-yes" open-type="agreePrivacyAuthorization" @agreeprivacyauthorization="onAgree">同意</button>
    </view>
  </view>
</template>
配置 / 机制作用注意
app.initPrivacyAuthorization隐私协议初始状态：auto / agree / disagree（默认 auto）auto 时各平台初始值不同：Android 与鸿蒙初始为 disagree，iOS 初始为 agree——所以要按平台验证，不能想当然
uni.getPrivacySetting读取隐私协议状态（返回 needAuthorization；privacyContractName 仅小程序端有）放在 onLaunch 里做首次判断
uni.resetPrivacyAuthorization重置隐私协议授权状态调试时很有用（不用每次卸载重装）
uni.onPrivacyAuthorizationChange / offPrivacyAuthorizationChange监听 / 取消监听隐私授权状态变化与第 10 章的网络状态监听一样：用完要记得取消监听
dialogPage官方示例用它承载隐私政策弹框dialogPage 不属于页面栈，不会被"返回"跳过（第 7 章讲过它的定位）
button 的 open-type="agreePrivacyAuthorization"把"同意"变成平台认可的授权动作不要用普通按钮 + 自己写状态，否则平台不认
平台兼容性微信小程序 4.41+、支付宝小程序 5.31+、Android / iOS 4.31+、鸿蒙 4.61+Web 端不支持这套隐私授权机制
!
首次启动的弹窗，还有四条硬要求：

① 必须以弹窗形式展示《隐私政策》/「个人信息保护指引」，并提供"同意"与"拒绝"两个选择， 而且"拒绝"不能被隐藏或弱化（做成灰色小字、只留同意按钮，都属于违规）； ② 国内应用商店要求"启动即弹"；Google Play 允许"仅在使用相关功能前弹"—— 上线前要看目标市场的要求； ③ 用户不同意时的处理不同：国内可以调用 uni.exit 退出应用， 但 App Store 非中国区不得因用户不同意而退出（应降级为"不提供需要该权限的功能"）； ④ 隐私政策里必须列举你内置的第三方 SDK（统计、地图、推送等）及其收集的信息—— 官方合规文档里提供了内置三方 SDK 清单可对照。

💡
写隐私政策文案的三个要点（不需要律师也能写对）：

① 收集什么：写清具体数据项（如"相册中的图片"、"设备型号与系统版本"）， 而不是含糊的"必要的用户信息"； ② 用来干什么：与功能一一对应（"图片用于发布商品"）； ③ 怎么联系你：留一个可用的邮箱或说明。 另外：第三方 SDK 也要写进去（例如你用了统计、地图、推送），并说明它们收集什么。

13.6

版本号：两个值，规则不一样

10 分钟 · 讲授
字段给谁看规则
versionName 用户（应用市场、关于页面显示的就是它） 字符串，习惯用 主.次.修订：1.0.0 → 1.1.0（加功能） → 1.1.1（修 bug）
versionCode 系统与商店（用来判断"哪个更新"） 必须是整数，取值 1~2147483647，升级时必须高于上一次的值——只能加不能减
!
三个真实的踩坑场景：

① 忘了加 versionCode 就重新提交：市场提示"版本号已存在"，无法上传； ② 把 versionCode 写成小数（如 1.1）：它不是数字类型，会直接失败； ③ 把 versionCode 改小"回滚版本"：系统会认为老包要覆盖新包，通常会被拒绝。 正确做法是：每次发版前先确认"上一个版本的 code 是多少"，然后加 1。

💡
课程项目的版本建议：

第一次交付：versionName 1.0.0 / versionCode 1； 答辩前一晚修完 bug 再发一次：1.0.1 / versionCode 2。 这样在你的演示里能自然说出"我们迭代了两个版本"，比"只打了一个包"更像一个真实项目。

进阶：发出去之后怎么更新？——热更新（wgt）

应用已经装到同学手机上了，你改了一个文案，难道还要他重新下载安装包？ 官方提供了 wgt 资源包热更新来解决这个问题（uni-app x 的 wgt 使用 zstd 格式）：

环节做法（官方口径）
制作HBuilderX 5.31+ 提供「发行 → App-制作 wgt 包」
安装uni.installWgt({ filePath, ignoreVersion })——仅 Android / iOS 的蒸汽模式、5.31+ 支持；Web 与小程序不支持
典型流程改 versionName → 生成 wgt → 用 uni.getAppBaseInfo() 的 appWgtVersion 比对版本 → uni.downloadFile 下载 → installWgt → getApp().restart() 重启生效
推荐做法官方推荐使用 uni 升级中心，避免自己从头实现"检查更新"的整套逻辑
!
热更新的三条边界，一定要知道：

① wgt 不能更新原生模块与 manifest——也就是说，改了图标、权限、minSdkVersion 这类配置，或者新增了 uts 插件，必须重新打整包发布，热更新解决不了； ② 审核期间不得使用热更新，否则会被视为绕过审核； ③ 不得通过热更新改变应用的性质（这是各商店的底线）。 所以正确的理解是：热更新用于"改内容"，整包用于"改能力"。

13.7

打包与签名：三种运行方式别搞混

20 分钟 · 讲授

先把"运行"这件事的三种形态分清楚——这是新手最混乱的地方：

形态是什么什么时候用限制
标准基座 官方预编译好的运行环境，装上就能跑你的代码 开发期天天用：改代码即时生效、不用打包 用的是官方包名与图标；看不到你自己配的图标/名称/权限效果（13.2 强调过）
自定义基座 用你自己的配置（包名、图标、权限、模块）打出来的调试包 当你的配置会影响运行时行为时（例如需要某个权限、接了 uts 插件） 打一次要等一会儿；配置改动后需要重新打
正式打包 产出可分发的安装包（Android 是 apk/aab，iOS 是 ipa） 要给同学装、要上架时 需要签名材料；iOS 还需要开发者账号与证书
ⓘ
关于签名，先建立正确的心智模型：

Android 与 iOS 的签名机制差别很大，但共同点是——签名用来证明"这个包确实是你发的"，并且后续更新必须用同一套签名。 所以：正式发布用的证书/密钥一定要备份好； 一旦丢失，你将无法给已上架的应用推送更新（只能换包名重新上架，老用户不会自动更新）。 这是很多团队真实踩过的坑，比任何配置错误都严重。

平台签名 / 凭证关键规则
Android 云证书（DCloud 按 appid 自动生成） 有效期很长（官方说明为 100 年），但证书信息不可自定义；省事，适合课程项目
自选证书（用 keytool 自己生成） 免费、信息可自定义（如公司名）；自己保管，丢了没人能帮你恢复
iOS Bundle ID + 私钥证书（p12 + 私钥密码）+ 证书 Profile 在 Apple 开发者网站申请；打包时至少勾选 iPhone / iPad
提交 ipa 必须走「发行 → App 云打包」；官方明确自定义调试基座不能当成正式包提交
ⓘ
官方文档里的打包路径（供你对照，界面可能随版本变化）：

云打包：「发行」→「App-Android / iOS-云打包」； 离线打包：需要在原生工程环境中配置（官方在原生使用文档里给了 Android / iOS 的配置说明）； 产物格式：Android 支持 APK 与 AAB，并可生成华为 / OPPO / vivo / 小米 / 荣耀 / 应用宝等渠道包。 另外官方 CLI 也支持打包（需先启动 HBuilderX）；是否"必须用 HBuilderX"官方文档没有直接表述， 本课程按 HBuilderX 流程讲解。

💡
顺带回答一个常见疑问："在 Windows 上能打 iOS 包吗？"

可以。云打包在 DCloud 的服务器上完成，你只需要在苹果开发者后台备好证书与 Profile，不必拥有一台 Mac。 另外官方还提供了多商店上传能力（覆盖 App Store、Google Play 与国内主要安卓市场），配合云打包能省掉不少手动流程。

!
打包前自查三件事（能省下大量等待时间）：

① 图标是否齐全：Android 四套 + iOS 的 1024，且都是 png、iOS 那版无透明； ② versionCode 是否已递增（13.6 的规则）； ③ 权限是否最小化（excludePermissions 清掉用不到的）。 官方还提醒了一点：只有"正式包"才能用于上架提交，自定义调试基座不能当正式包—— 所以"能装上"不等于"能交审"。至于具体菜单入口，各版本 HBuilderX 略有差异，以你所用版本的官方文档为准。

13.8

多端发布：一份代码，四种去处

15 分钟 · 讲授

这正是 uni-app x 的价值所在——同一套代码可以发布到多个平台。 但"能发布"不等于"随便发"，每个平台的产物与准备材料都不同：

目标平台产物需要的准备材料提交去向
Android App apk / aab 安装包 应用图标（四套 png）、签名证书、隐私政策、应用截图与简介 各 Android 应用市场（华为、小米、OPPO、vivo、应用宝等）分别提交
iOS App ipa（上传到 App Store Connect） Apple 开发者账号、证书与描述文件、1024 无透明图标、隐私说明 App Store（审核较严格，隐私与权限说明要写清）
Web / H5 静态文件（SPA 单页应用资源） 一个能放静态文件的服务器或对象存储（也可用 uniCloud 的"前端网页托管"） 自行部署后把网址发给同学（扫码即用，无需安装）。注意：兼容转化只在发行时进行
小程序 小程序代码包 小程序 AppID、request / uploadFile / downloadFile 的合法域名（第 8 章强调过，三者是分开配的）；上传密钥在小程序后台「开发管理 → 开发设置」里获取 上传到对应平台提交审核。官方兼容性：4.41+ 支持微信小程序、5.31+ 支持支付宝小程序；用 HBuilderX 上传时可免开微信开发者工具
HarmonyOS 已签名的 .app 包 鸿蒙开发者账号、DevEco Studio（官方文档给出所需版本区间）与相应配置（见 manifest 的 app-harmony 文档） 官方路径为「发行」→「App-Harmony-本地打包」得到已签名包，再提交华为应用市场。HarmonyOS 支持从 4.61+ 起
ⓘ
两条与这门课直接相关的提醒：

① Web 端与小程序端目前仍按 VDOM 模式运行（第 1 章与附录 C 都强调过）， 所以"在浏览器里正常"不代表在 App 里正常，反之亦然——多端发布前必须逐端回归； ② 小程序端最容易被卡住的不是代码，而是域名白名单： 把接口域名加进 request 合法域名，把上传域名加进 uploadFile 合法域名，两者是不同的配置项。

💡
课程项目的最优交付策略：

如果你没有开发者账号（iOS 需要年费会员）， 推荐"Android apk + Web 部署"两条线： apk 可以直接发给同学安装（真实体验），Web 版本可以用链接演示（答辩时最方便）。 这也顺带说明了 uni-app x 的实用之处：同一份代码，两种交付方式同时拥有。

ⓘ
上架还有个"省事通道"：多商店上传。

官方提供了多商店上传能力，覆盖 App Store、Google Play、华为、荣耀、小米、vivo、OPPO、应用宝、魅族； 与云打包配合，即使没有 Mac 也能完成 App Store 的上架流程。 另外官方维护了一个"应用市场"文档页，汇总了华为 / 小米 / OPPO / vivo / 荣耀 / 苹果的官方审核规范、资质要求与 App 备案入口—— 提交前照着对一遍，比自己摸索快得多。注意：各商店的规则会不定期更新，务必以官方链接的最新版为准。

结课：这门课的知识地图与结课作业

15 分钟 · 总结 + 布置

📌 这一章记住五句话

manifest.json 是项目身份证，uni-app-x 节点必须存在，versionCode 必须是整数且只能递增； Android 图标四套（72/96/144/192）与 iOS 的 1024 都必须是 png，iOS 那版不能有透明区域； 权限要最小化（用 excludePermissions 清掉用不到的），targetSdkVersion 要满足目标市场要求； uni-app x 无需配置原生隐私弹框、自行弹框即可，但同意隐私政策前绝不能采集数据—— 这是上架的红线，官方原话是"会无法上架甚至被处罚"； 打包与签名材料要提前准备并安全备份，丢了证书就无法给已上架的应用推更新。

12.1

先看清这个项目"难在哪"

15 分钟 · 讲授

把项目①和项目②放在一起对比，你会立刻明白"多一个后端"意味着什么：

对比项项目① 课程表（本地）项目② 二手交易（联网）
数据来源自己写、自己读（本地存储）别人给（接口返回的 JSON，字段名你说了不算）
会不会失败几乎不会（最多解析失败）随时会：超时、断网、服务端 500、token 过期

首屏能不能秒开能（本地读取）不能，所以需要三态 + 缓存 + 骨架屏

12.2

最真实的坑：接口字段和你以为的不一样

25 分钟 · 讲授 + 动手

新手接接口最常见的失败不是"请求发不出去"，而是请求成功了、界面却渲染不出来或显示 undefined。 原因通常有三类，我们一个一个解决。

问题典型表现解决办法
① 结构假设错误 你写 res.data.list，实际是 res.data.data.records 第一步永远是打印完整结构：console.log(JSON.stringify(res.data))，看清之后再写代码
② 字段名风格不同 后端给 cover_url / createTime，前端习惯 coverUrl 在 api 层集中转换一次，页面里只用统一的前端字段名
③ 空值与类型不一致 价格有时是数字 35、有时是字符串 "35.00"；描述可能为 null 转换时统一兜底（?? ''、Number(...)），并只在一处做
types/goods.ts —— 前端自己的一套类型（页面只用它） 
// 前端内部的统一模型：字段名、类型、空值规则都在这里定死
export type Goods = {
  id: number,
  title: string,
  price: number,           // 一律用"元"为单位的数字，展示时再格式化
  coverUrl: string,        // 没有图时给空字符串（不要用 null，避免到处判空）
  category: string,
  desc: string,
  sellerName: string,
  status: string,          // on_sale 在售 / sold 已售 / off 已下架
  createdAt: number        // 一律用时间戳（数字），格式化交给界面
}

// 服务端可能给的东西（字段名以对方为准，这里按常见的下划线风格举例）
export type GoodsDto = {
  'id': number,
  'title': string,
  'price': number | string,
  'cover_url': string | null,
  'category'?: string,
  'description'?: string,
  'seller_name'?: string,
  'status'?: string,
  'create_time'?: number
}

// 统一的转换函数：所有"脏活"都在这里做完
export const toGoods = (dto: GoodsDto): Goods => {
  return {
    'id': dto.id,
    'title': dto.title ?? '',
    // 价格可能是字符串（如 "35.00"），统一转成数字
    'price': typeof dto.price == 'string' ? Number.parseFloat(dto.price as string) : dto.price as number,
    'coverUrl': dto.cover_url ?? '',
    'category': dto.category ?? '其他',
    'desc': dto.description ?? '',
    'sellerName': dto.seller_name ?? '同学',
    'status': dto.status ?? 'on_sale',
    'createdAt': dto.create_time ?? 0
  }
}

// 列表也要转换：页面永远拿不到 DTO
export const toGoodsList = (list: GoodsDto[]): Goods[] => {
  const out: Goods[] = []
  for (let i = 0; i < list.length; i++) {
    out.push(toGoods(list[i]))
  }
  return out
}
✓
这一节的真正价值：把"丑陋"关在一个文件里。

现实中的接口字段往往不统一、还会变。如果你在每个页面里都去适配字段名， 那么后端改一次字段，你就要改 N 个页面（而且一定会漏一个）。 正确做法就是这一节写的：接口原始结构（DTO）→ 一次转换 → 前端自己的模型（Goods）， 页面只认 Goods。这个模式在任何语言的前端项目里都通用。

💡
额外提醒：价格别用小数直接算。

金额在计算机里用浮点数做加减会出现 0.1 + 0.2 = 0.30000000000000004 这种结果。 本项目只是展示价格，用 Number 够了；但一旦涉及"总价、优惠、分账"， 就应该用整数分来计算（后端通常也是这么存的），展示时再除以 100。 这是一条以后会救你的经验。

12.3

网络层分层：页面里不该出现 uni.request

25 分钟 · 讲授 + 动手

第 8 章我们封了一个 request，第 9 章加了 token 与 401。这一章往上再叠一层：api 模块。

utils/request.ts —— 第 8 + 9 章的成果（基础层） 
// 只负责：拼域名、超时、token、两层判断、错误提示、返回"业务数据"或 null
export const request = <T>(options: RequestOptions): Promise<T | null> => {
  return new Promise<T | null>((resolve) => {
    uni.request({
      'url': BASE_URL + options.url,
      'method': options.method ?? 'GET',
      'data': options.data ?? null,
      'timeout': 10000,
      'header': {
        'Content-Type': 'application/json',
        'Authorization': 'Bearer ' + getToken()          // 从存储读，不硬编码
      },
      'success': (res) => {
        if (res.statusCode == 401) {                     // 登录失效：统一处理
          clearLogin()
          gotoLogin()
          resolve(null)
          return
        }
        if (res.statusCode != 200) {
          if (options.showError !== false) toast('服务异常（' + res.statusCode + '）')
          resolve(null)
          return
        }
        const body = res.data as UTSJSONObject
        if ((body['code'] as number) != 0) {             // 业务码
          if (options.showError !== false) toast((body['msg'] as string) ?? '请求失败')
          resolve(null)
          return
        }
        resolve(body['data'] as T)
      },
      'fail': (err) => {
        if (options.showError !== false) toast(friendlyError(err.errCode))
        resolve(null)
      }
    })
  })
}
api/goods.ts —— 业务层（页面只用这一层） 
import { request } from '@/utils/request'
import { toGoods, toGoodsList } from '@/types/goods'

// 列表返回：服务端给 { list, total }
type PageDto = { 'list': GoodsDto[], 'total': number }
export type PageResult = { 'list': Goods[], 'total': number }

// 商品列表（带分页与筛选）
export const fetchGoodsList = async (
  page: number,
  size: number,
  keyword: string,
  category: string
): Promise<PageResult | null> => {
  // 注意：App-Android 端 data 必须是对象或字符串（第 8 章）
  const data = await request<PageDto>({
    'url': '/goods/list',
    'data': { 'page': page, 'size': size, 'keyword': keyword, 'category': category }
  })
  if (data == null) return null
  // 转换就在这里完成，页面拿到的一定是 Goods[]
  return { 'list': toGoodsList(data.list), 'total': data.total }
}

// 商品详情
export const fetchGoodsDetail = async (id: number): Promise<Goods | null> => {
  const dto = await request<GoodsDto>({ 'url': '/goods/detail', 'data': { 'id': id } })
  if (dto == null) return null
  return toGoods(dto)
}

// 发布商品（返回新商品 id）
export const publishGoods = async (payload: PublishPayload): Promise<number | null> => {
  // 发布是不可重复的操作：失败时不要自动重试
  const res = await request<UTSJSONObject>({
    'url': '/goods/create',
    'method': 'POST',
    'data': payload as UTSJSONObject
  })
  if (res == null) return null
  return res['id'] as number
}

// 下架自己的商品
export const offShelf = async (id: number): Promise<boolean> => {
  const res = await request<UTSJSONObject>({
    'url': '/goods/off',
    'method': 'POST',
    'data': { 'id': id }
  })
  return res != null
}
层职责不允许做的事
页面 / 组件展示数据、响应用户操作、维护界面状态不拼 url、不判断 statusCode、不做字段转换
api 模块（api/goods.ts）描述"有哪些接口、参数是什么、返回什么类型"，并做 DTO → 模型的转换不写界面逻辑、不弹 toast（提示交给 request 层或页面）
request 层（utils/request.ts）域名、超时、token、两层判断、错误提示、401 跳登录不知道任何业务概念（不该出现"商品""订单"这些词）
💡
怎么判断"我分层分对了"？

做三个小测试：① 把接口域名从测试环境换到生产环境，需要改几个文件？（应该只有 1 个） ② 后端把 cover_url 改成 coverImage，需要改几个文件？（1 个） ③ 找出所有"判断登录失效并跳登录页"的代码，有几处？（1 处） 三个答案都是"1"，说明分层是对的。

12.4

列表页：把第 8 章的坑一次全踩对

30 分钟 · 讲授 + 演练

二手交易的首页要同时满足五件事，缺一个都会被用户骂：

  1. 三态齐全：加载中、失败（可重试）、空态（"还没有人发布"）
  2. 分页正确：触底加载、加锁防重复、没有更多时给提示
  3. 搜索不抖：输入时不每敲一个字就请求一次
  4. 分类切换不出错：快速切换时只显示最后一次的结果（请求竞态）
  5. 下拉刷新：回到第一页并显示最新数据
pages/index/index.uvue —— 列表页核心逻辑 
<script setup>
  import { fetchGoodsList } from '@/api/goods'

  const list = ref<Goods[]>([])
  const page = ref<number>(1)
  const loading = ref(false)
  const noMore = ref(false)
  const error = ref<string>('')
  const keyword = ref<string>('')
  const category = ref<string>('全部')

  const SIZE = 10
  // 请求序号：解决"快速切换分类时显示过期结果"（第 8 章的竞态处理）
  let seq = 0

  const loadPage = async (p: number) => {
    seq = seq + 1
    const current = seq
    loading.value = true
    error.value = ''

    const res = await fetchGoodsList(p, SIZE, keyword.value, category.value)

    // 回来时如果序号变了，说明用户已经切换了条件：本次结果直接丢弃
    if (current != seq) return

    loading.value = false
    if (res == null) {
      // 只有在"第一页就失败"时才显示整页错误（后续页失败保留已有数据）
      if (p == 1) error.value = '加载失败，请检查网络后重试'
      return
    }
    // 第一页替换、后续页追加（第 8 章的分页要点）
    list.value = p == 1 ? res.list : list.value.concat(res.list)
    noMore.value = list.value.length >= res.total || res.list.length < SIZE
  }

  const reload = () => {
    page.value = 1
    noMore.value = false
    list.value = []
    loadPage(1)
  }

  // 搜索防抖：停止输入 400ms 后才真正请求
  let timer: number = -1
  const onKeywordInput = (event: UniInputEvent) => {
    keyword.value = event.detail.value
    if (timer != -1) clearTimeout(timer)
    timer = setTimeout(() => { reload() }, 400)
  }

  const switchCategory = (c: string) => {
    if (category.value == c) return
    category.value = c
    reload()                       // 靠 seq 保证只认最后一次
  }

  onReachBottom(() => {
    if (loading.value || noMore.value) return       // 双重锁
    const next = page.value + 1
    loadPage(next).then(() => { page.value = next })  // 拿到结果才推进页码
  })

  onPullDownRefresh(async () => {
    reload()
    uni.stopPullDownRefresh()
  })

  onLoad(() => { reload() })

  // 页面卸载时清掉定时器（第 7 章的教训）
  onUnload(() => { if (timer != -1) clearTimeout(timer) })
</script>
!
防抖与竞态是两件事，别混：

防抖（debounce）解决"请求次数太多"——输入过程中不要每次都发请求； 竞态处理（请求序号 / abort）解决"结果顺序错乱"——即使只发了一次请求， 在分类切换这种场景下，后发的结果也可能先回来。 两个都要做：防抖让请求变少，序号让结果永远正确。

💡
更省事的搜索：把"搜索"变成一次接口调用。

上面用 keyword 参数请求服务端搜索，适合数据量大（几百上千条）的场景。 如果你们的数据只有几十条，也可以一次性取回后在本地过滤（computed + includes）， 代码更短、体验更快，但数据量一大就不行了。 两种方案都要会，选择依据是数据规模——这也是技术选型的通用思路。

12.5

发布页：多图上传是本项目最难的一页

35 分钟 · 讲授 + 演练

上传图片这件事，新人通常写成"选图 → 循环上传 → 全部成功后再提交"， 结果一遇到"第 2 张失败"就整页卡住、用户也不知道该怎么办。正确做法是把每一步的状态都管起来。

要处理的情况做法
图片太大选图时用 sizeType: ['compressed']，上传前再 compressImage 压一次
某张上传失败逐张单独管理状态：每张有自己的 status（待上传 / 上传中 / 成功 / 失败）与"重试"按钮
用户重复点提交提交中用 submitting 锁 + 按钮 :disabled
上传很慢显示进度（uploadFile 的 onProgressUpdate）与"上传中"文案
提交后发现少传了图先全部传完图，拿到图片地址列表，再提交表单——顺序不能反
中途退出页面提示"有未发布的内容，确定离开？"（可用 uni.showModal + 页面返回拦截思路）
pages/publish/publish.uvue —— 多图上传的完整状态管理 
<script setup>
  import { publishGoods } from '@/api/goods'

  // 一张待上传的图片，自带状态（这是"能重试"的关键）
  type UploadItem = {
    path: string,          // 本地临时路径
    status: string,        // waiting / uploading / done / fail
    remoteUrl: string,     // 上传成功后拿到的服务器地址
    sizeKb: number
  }

  const images = ref<UploadItem[]>([])
  const MAX_IMG = 3

  const form = reactive({ 'title': '', 'price': '', 'desc': '', 'category': '教材' })
  const submitting = ref(false)

  /* ---------- ① 选图（压缩图 + 限制张数） ---------- */
  const pickImages = () => {
    const left = MAX_IMG - images.value.length
    if (left <= 0) {
      toast('最多 ' + MAX_IMG + ' 张图')
      return
    }
    uni.chooseImage({
      'count': left,
      'sizeType': ['compressed'],                  // 先要压缩图，省流量
      'sourceType': ['album', 'camera'],
      'success': (res) => {
        const next: UploadItem[] = []
        for (let i = 0; i < res.tempFilePaths.length; i++) {
          next.push({
            'path': res.tempFilePaths[i],
            'status': 'waiting',
            'remoteUrl': '',
            'sizeKb': Math.round(res.tempFiles[i].size / 1024)
          })
        }
        images.value = images.value.concat(next)
      },
      'fail': (err) => {
        // 1101001 用户取消：静默；1101005 未授权：引导（第 10 章）
        if (err.errCode == 1101005) toast('需要相册权限')
      }
    })
  }

  /* ---------- ② 单张上传（失败可重试） ---------- */
  const uploadOne = (index: number): Promise<void> => {
    return new Promise((done) => {
      const item = images.value[index]
      item.status = 'uploading'

      // 可选：先压缩再传（大图必做）
      uni.compressImage({
        'src': item.path,
        'quality': 70,
        'success': (c) => { doUpload(index, c.tempFilePath, done) },
        'fail': () => { doUpload(index, item.path, done) }        // 压缩失败就用原图
      })
    })
  }

  const doUpload = (index: number, filePath: string, done: () => void) => {
    const task = uni.uploadFile({
      'url': BASE_URL + '/upload',
      'filePath': filePath,
      'name': 'file',
      'header': { 'Authorization': 'Bearer ' + getToken() },
      'success': (res) => {
        if (res.statusCode != 200) {
          images.value[index].status = 'fail'
          done()
          return
        }
        // 后端一般返回 { code: 0, data: { url: '...' } }
        const body = JSON.parse(res.data) as UTSJSONObject
        const data = body['data'] as UTSJSONObject
        images.value[index].remoteUrl = data['url'] as string
        images.value[index].status = 'done'
        done()
      },
      'fail': () => {
        images.value[index].status = 'fail'      // 标记失败，界面上给"重试"
        done()
      }
    })
    // 进度回调：让用户看到"正在上传"
    task.onProgressUpdate((p) => {
      console.log('第 ' + (index + 1) + ' 张：' + p.progress + '%')
    })
  }

  const retry = (index: number) => {
    uploadOne(index)
  }

  /* ---------- ③ 提交：先保证图片全部上传成功 ---------- */
  const canSubmit = computed<boolean>((): boolean => {
    const okForm = form.title.length >= 4 && Number.parseFloat(form.price) > 0
    const okImg = images.value.length > 0
    return okForm && okImg && !submitting.value
  })

  const submit = async () => {
    if (!canSubmit.value) return
    submitting.value = true                       // 锁：防止重复提交

    // ① 先把还没传的图全部传完
    for (let i = 0; i < images.value.length; i++) {
      if (images.value[i].status != 'done') {
        await uploadOne(i)
      }
    }

    // ② 检查是否全部成功
    const failed = images.value.filter((it) => it.status != 'done')
    if (failed.length > 0) {
      submitting.value = false
      uni.showModal({ 'title': '有图片上传失败', 'content': '请点击图片上的"重试"后再提交', 'showCancel': false })
      return
    }

    // ③ 收集图片地址并提交表单
    const urls: string[] = []
    for (let i = 0; i < images.value.length; i++) {
      urls.push(images.value[i].remoteUrl)
    }
    const id = await publishGoods({
      'title': form.title,
      'price': Number.parseFloat(form.price),
      'desc': form.desc,
      'category': form.category,
      'images': urls
    })

    submitting.value = false
    if (id == null) {
      toast('发布失败，请稍后重试（内容已保留）')     // 关键：不要清空表单
      return
    }
    uni.showToast({ 'title': '发布成功', 'icon': 'success' })
    // 回到首页并刷新列表
    uni.switchTab({ 'url': '/pages/index/index' })
  }
</script>
✕
发布失败后千万不要清空表单。

用户填了 200 字的描述、传了 3 张图，你一句"发布失败"就把输入清掉—— 这是最容易被骂的设计。正确做法是保留全部内容并提示失败原因， 让用户只按一次"重试"就能继续。 更进阶的做法是把草稿存进本地存储（第 9 章），用户下次进来还能恢复。

详情页与收藏：一个关于"数据放哪"的取舍

pages/goods-detail/detail.uvue —— 按 id 请求详情 
<script setup>
  import { fetchGoodsDetail } from '@/api/goods'

  const goods = ref<Goods | null>(null)
  const loading = ref(true)
  const error = ref('')
  const goodsId = ref<number>(-1)

  onLoad((options: OnLoadOptions) => {
    const idStr = options['id'] ?? ''
    if (idStr.length == 0) {
      error.value = '缺少商品参数'
      loading.value = false
      return
    }
    goodsId.value = Number(idStr)
    load()
  })

  const load = async () => {
    loading.value = true
    error.value = ''
    const g = await fetchGoodsDetail(goodsId.value)
    loading.value = false
    if (g == null) {
      error.value = '商品不存在或已被删除'
      return
    }
    goods.value = g
  }

  // 收藏：只存 id 列表（第 9 章）
  const isFav = ref(false)
  const KEY_FAV = 'app_fav_goods'

  const loadFav = () => {
    const raw = uni.getStorageSync(KEY_FAV) as string
    if (raw.length == 0) return
    try {
      const ids = JSON.parse(raw) as number[]
      isFav.value = ids.includes(goodsId.value)
    } catch (e) {
      console.log('收藏数据异常，忽略')
    }
  }

  const toggleFav = () => {
    const raw = uni.getStorageSync(KEY_FAV) as string
    let ids: number[] = []
    if (raw.length > 0) {
      try { ids = JSON.parse(raw) as number[] } catch (e) { ids = [] }
    }
    if (isFav.value) {
      ids = ids.filter((x) => x != goodsId.value)
    } else {
      ids.push(goodsId.value)
    }
    uni.setStorageSync(KEY_FAV, JSON.stringify(ids))
    isFav.value = !isFav.value
    toast(isFav.value ? '已收藏' : '已取消收藏')
  }

  onPageShow(() => { loadFav() })
</script>
数据本项目放哪为什么
商品列表 / 详情 服务端（每次请求） 别人随时可能发布、下架、改价；本地存一份一定会过期
登录 token 本地存储 + 全局状态 重启后要还在；同时要能被请求层读取（第 9 章）
收藏（id 列表） 本地存储（本项目） 只有本人关心、数据很小；代价是换手机就没了——真实产品会放服务端，本项目为控制规模放本地，需在文档里写明取舍
搜索历史 / 浏览历史 本地存储 属于"个人偏好"，不上传更符合隐私直觉
草稿（未发布的商品） 本地存储 发布失败或误退出时要能恢复（12.5 的进阶做法）
💡
"收藏放本地还是放服务端"是一个很好的答辩问题。

放本地：实现快、不耗流量、不需要登录；换设备就丢、无法跨端同步。 放服务端：跨设备同步、能算"收藏数"；需要登录、需要接口、多一次请求。 能说清两种方案的取舍，并把你的选择写进设计说明，比"随便选一个"更有说服力。 这正是本项目刻意留出的"设计决策点"。

// 用法：if (!ensureLogin()) return
// 返回 true 表示已登录；返回 false 表示已引导去登录，调用方直接 return 即可
export const ensureLogin = (tip: string): boolean => {
  const token = getToken()
  if (token.length > 0) return true

  uni.showModal({
    'title': '需要登录',
    'content': tip,
    'confirmText': '去登录',
    'success': (r) => {
      if (r.confirm) {
        // 登录页是非 tab 页面，用 navigateTo 保留当前页，登录后返回
        uni.navigateTo({ 'url': '/pages/login/login' })
      }
    }
  })
  return false
}

<script setup>
  import { request } from '@/utils/request'
  import { saveLogin } from '@/utils/auth'

  const phone = ref('')
  const code = ref('')                 // 校园项目最省事的登录方式：手机号 + 验证码
  const counting = ref(0)
  const submitting = ref(false)

  const canLogin = computed<boolean>((): boolean => {
    return phone.value.length == 11 && code.value.length >= 4 && !submitting.value
  })

  const sendCode = () => {
    if (phone.value.length != 11) { toast('请输入 11 位手机号'); return }
    counting.value = 60
    const t = setInterval(() => {
      counting.value = counting.value - 1
      if (counting.value <= 0) clearInterval(t)
    }, 1000)
    // 真实项目这里调用发送验证码接口
  }

  const login = async () => {
    if (!canLogin.value) return
    submitting.value = true
    const res = await request<UTSJSONObject>({
      'url': '/login',
      'method': 'POST',
      'data': { 'phone': phone.value, 'code': code.value }
    })
    submitting.value = false
    if (res == null) return

    // 保存 token 与用户信息（第 9 章：本地存储 + 全局状态）
    const token = res['token'] as string
    const user = res['user'] as UTSJSONObject
    const name = user['name'] as string
    saveLogin(token, { 'id': user['id'] as number, 'name': name })

    uni.showToast({ 'title': '登录成功', 'icon': 'success' })
    // 返回上一页；上一页的 onPageShow 会刷新（第 7 章）
    setTimeout(() => { uni.navigateBack() }, 600)
  }
</script>

"拦截时机"比"拦截逻辑"更重要：

两种做法对比：等用户填完表单再告诉他"请先登录" —— 用户会非常恼火（白填了）； 点进发布页/点发布按钮时就拦截 —— 用户只损失一次点击。 原则是：越早告知越好，越晚代价越大。 同理，涉及权限（相机、定位）也应该在"用到它的那一刻"就申请，而不是等用户填完再说。

📌 这个项目你真正学到的，浓缩成 6 句话

联网项目的第一原则：永远先打印接口返回的完整结构，再写渲染代码； 把接口的"脏"关起来——用 DTO → 转换函数 → 前端模型，页面只认自己定义的字段名与类型； 网络层要分层：request（域名/超时/token/401/错误提示）→ api（接口+转换）→ 页面（只做展示与交互）， 判断标准是"换域名 / 改字段 / 改登录失效处理"各自都只改一个文件； 列表要同时解决四件事：三态、分页加锁、搜索防抖、请求竞态（序号或 abort）， 其中防抖管"请求多少"，序号管"结果对不对"； 多图上传必须逐张管理状态（待传/上传中/成功/失败 + 单张重试）， 并且先传完图拿到地址再提交表单，发布失败绝不能清空用户填的内容； 最后：登录拦截要早（点按钮时就拦，而不是填完表单才拦）， 收藏这类数据的"放本地还是放服务端"是一个需要写进设计说明的取舍。

先打印再渲染 DTO → 模型 字段集中转换 价格用整数分 request/api/页面三层 分页双重锁 搜索防抖 请求序号防竞态 逐张上传状态机 单张重试 失败保留表单 先传图再提交 登录拦截时机 收藏取舍 弱网验证

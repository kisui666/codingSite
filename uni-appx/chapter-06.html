组件化开发与组件通信：把界面拆成可复用的零件

前五章你已经能做出完整页面了。但从"能写"到"能维护"，中间隔着一件事：组件化。 这一章讲三件事：怎么创建与自动引入组件（easycom）、 父与子之间怎么传数据（props 向下、回调向上、ref 调用方法）、 以及什么时候该用哪种通信方式。学完这一章，你的项目会从"一堆页面"变成"一套零件"。

6.1

组件化：从"能写"到"能维护"

15 分钟 · 讲授

先看一段真实会发生的场景：你的课程列表页里，"课程卡片"这段结构写了 4 遍—— 首页一遍、搜索页一遍、收藏页一遍、详情页底部推荐一遍。某天产品说"卡片上要加一行教师名"， 你就要改 4 个地方；改漏一个，用户就会看到一个不一致的界面。 组件化解决的就是这个问题。

组件和页面：四点差别，先记清楚

对比项页面（在 pages.json 注册的 uvue）组件（components 里的 uvue）
是否需要注册 必须在 pages.json 里注册才能访问 不需要注册（符合 easycom 规则即可直接用）
页面生命周期 支持 onLoad / onReady / onPageShow / onUnload 等 不支持页面生命周期，也不能用 $setPageStyle 这类页面 API
组件生命周期 — 有自己的一套：onMounted / onUnmounted / onBeforeUnmount 等
复用与嵌套 可以被当作组件引入到别的页面里（页面也能当组件用） 能嵌套组件、能被多处复用
ⓘ
官方还有一个值得知道的细节：

用组合式 API 写的组件，可以监听它所在页面的页面级生命周期（选项式则不行）。 也就是说，组件里想"页面显示时刷新一下"，可以用组合式的方式拿到页面生命周期—— 第 7 章会讲具体钩子。这也是官方推荐新代码用组合式的原因之一。

💡
什么该抽成组件？三个信号：

① 同一段界面出现两次以上（课程卡片、信息行、空状态提示）； ② 一段界面自带逻辑（比如"倒计时组件"自己管时间）； ③ 一个页面的模板超过 150 行，已经看不清结构了。 反过来，只用一次、也没有独立逻辑的东西，不要急着抽——那只会增加跳转文件的次数。

6.2

easycom：写完文件就能用，不用 import 也不用注册

20 分钟 · 讲授 + 动手

传统 Vue 组件要"安装 → 引入 → 注册"三步才能用。easycom 把它压缩成一步： 只要目录和名字符合规范，直接在模板里写标签就能用。

放哪里目录结构要求模板里怎么写
项目根目录 components/ components/course-card/course-card.uvue
（组件名/组件名.uvue）		 <course-card />
uni_modules/插件id/components/插件id/ uni_modules/uni-link-x/components/uni-link/uni-link.uvue <uni-link />
pages/ 下任意位置 可以直接建 .uvue 当组件用，但不符合 easycom 规则 需要手动 import 与使用
创建与使用组件的完整流程 
campus-app/
├─ components/                     ← 在项目根目录新建（没有就手动建一个）
│  └─ course-card/                 ← 组件名同名目录
│     └─ course-card.uvue          ← 组件文件（同名）
├─ pages/
│  └─ list/
│     └─ list.uvue                 ← 页面里直接写 <course-card> 即可
└─ pages.json                      ← 组件不需要在这里注册

# 提示：在 HBuilderX 里对着 components 目录右键 → 新建组件，
# 输入组件名后勾选"创建同名目录"，目录结构会自动符合 easycom 规范。
<template>
  <view class="page">
    <!-- 不写 import、不写注册，直接用；属性名用短横线写法 -->
    <course-card
      v-for="item in list"
      :key="item.id"
      :name="item.name"
      :teacher="item.teacher" />
  </view>
</template>

<script setup>
  // 这里完全没有 import 语句
  type Course = { id: number, name: string, teacher: string }
  const list = ref<Course[]>([])
</script>
<!-- 不符合 easycom 规范的组件（例如放在 pages 目录下）：需要手动引入 -->
<template>
  <view>
    <child ref="childRef"></child>
  </view>
</template>

<script setup>
  import child from './child.uvue'

  // 手动引入的组件，ref 类型是 ComponentPublicInstance
  const childRef = ref<ComponentPublicInstance | null>(null)
</script>
ⓘ
两个容易忽略的规则：

① 同名文件 .vue 与 .uvue 同时存在时，.uvue 优先编译—— 从老项目迁移时别把两个文件都留着； ② 如果你的组件目录不符合规范，也可以在 pages.json 里声明自己的 easycom 目录规则， 让编译器找得到它。

💡
命名建议：

组件名用多段短横线表达层级，例如 course-card、form-row、empty-tip； 自己的业务组件加个前缀（如 app-）能避免与插件市场的组件重名。 另外官方给出了 ref 的类型命名规范：组件标签名首字母大写 + 驼峰 + ComponentPublicInstance （例如 <test/> 对应的类型是 TestComponentPublicInstance）， 这样写 ref 时类型才对得上。

6.3

父传子：props 与"透传"机制

20 分钟 · 讲授 + 演练

props 是父组件向子组件传数据的唯一正规入口。写法你已经见过（第 3 章用过）， 这里把细节补全：类型怎么写、默认值怎么给、以及"没声明成 props 的属性会去哪儿"。

components/course-card/course-card.uvue —— props 的完整写法 
<template>
  <view class="card" hover-class="card-hover">
    <text class="name">{{ name }}</text>
    <text class="meta">{{ teacher }} · {{ room }}</text>

    <!-- 可选 prop：父层不传时用默认值 0 -->
    <text class="count">{{ count }} 人已选</text>

    <!-- 类型可选：不传就不显示 -->
    <view v-if="type.length > 0" class="tag"><text class="tag-text">{{ type }}</text></view>
  </view>
</template>

<script setup>
  // ① 必传与可选：可选参数用 ? 标记
  type CardProps = {
    name: string,
    teacher: string,
    room: string,
    type: string,
    count?: number
  }

  // ② 给可选参数默认值：官方写法是 withDefaults 包住 defineProps
  const props = withDefaults(defineProps<CardProps>(), {
    count: 0
  })

  // ③ 组合式里用点操作符访问：props.name
  //    （选项式里 $props 是 Map，要写 this.$props["name"]）
  const summary = computed(() => props.teacher + ' · ' + props.room)
</script>

<style>
  .card {
    background-color: #FFFFFF;
    border-radius: 12px;
    padding: 16px;
    margin-bottom: 10px;
  }
  .card-hover { background-color: #E9F0FF; }
  .name { font-size: 16px; font-weight: bold; margin-bottom: 4px; }
  .meta { font-size: 12px; color: #5A6B8C; margin-bottom: 6px; }
  .count { font-size: 12px; color: #A8B0BF; margin-bottom: 8px; }
  .tag { background-color: #E9F0FF; border-radius: 6px; padding: 2px 8px; align-self: flex-start; }
  .tag-text { font-size: 11px; color: #1E4FD8; }
</style>
✕
props 是单向的：子组件不要直接改它。

数据"由父传给子"，所以修改也应该发生在父组件。 如果子组件直接改 props，父组件那份数据不会跟着变，界面就会出现"两个地方显示不一致"的诡异问题。 正确做法是：子组件通过回调或事件通知父组件（下一节就讲），由父组件去改自己的数据。 这是最容易在项目中期变成技术债的一条规则。

attrs 透传：没声明成 props 的属性去哪儿了？

这是官方文档里一个很容易被忽略、但实际很有用的机制： 父组件传下来的、没有被子组件声明为 props 的属性，会"透传"到子组件的根节点上。

透传的实际效果（组件是单根节点时） 
<!-- 父层：class 与 id 都没有在组件的 props 里声明 -->
<course-card class="highlight" id="first-card" name="移动应用开发" />

<!-- 组件模板（单根节点） -->
<template>
  <view class="card">
    <text>{{ name }}</text>
  </view>
</template>

<!-- 实际渲染结果：class 会与组件根节点的 class 合并，id 也会落上去 -->
<!-- 也就是说：外部可以通过传 class 微调组件根节点的样式 -->

<!-- 如果不希望这种透传，官方文档指向 inheritAttrs 选项来关闭 -->
<!-- 详见官方「选项式 API」文档中的 inheritAttrs 一节 -->
ⓘ
这和第 3 章的样式隔离怎么对应？

两者说的是不同层面： 透传（attrs）管的是"父层写在组件标签上的 class / style / 其他属性"， 在单根节点组件上会落到根节点；样式隔离策略管的是"组件内部 .foo 这种 class 能不能被外部影响"。 所以：想改组件外框 → 传 class；想改组件内部某个元素 → 用 externalClasses 开口子（第 3 章）。 多根节点组件则需要组件内部自己决定把这些属性分配给谁。

6.4

子传父：向组件传递回调函数

20 分钟 · 讲授 + 演练

子组件要"通知父组件做点事"，官方文档给出的方式是： 父层在组件上写一个 @callback，子组件把它声明成 props 并直接调用。 本质就是"父层把一个函数交给子组件保管"。

子传父：父层给函数，子组件调用它 
<template>
  <view class="page">
    <text class="muted">子组件传来的值：{{ value }}</text>

    <!-- 核心：把父层的函数通过 @callback 交给子组件 -->
    <like-button :count="count" @callback="onLike" />
  </view>
</template>

<script setup>
  const value = ref<string>('')
  const count = ref<number>(0)

  // 子组件调用它时，参数会传进来
  const onLike = (msg: string) => {
    value.value = msg
    count.value = count.value + 1          // 数据由父层维护
  }
</script>
<!-- components/like-button/like-button.uvue -->
<template>
  <button class="like" @click="handleClick">点赞（{{ count }}）</button>
</template>

<script setup>
  type LikeProps = {
    count: number,
    // 把父层传进来的函数声明成 prop（函数类型这样写）
    callback?: (msg: string) => void
  }

  const props = withDefaults(defineProps<LikeProps>(), {
    count: 0
  })

  const handleClick = () => {
    // 只负责"通知"，不负责改数据
    if (props.callback != null) {
      props.callback('子组件被点了第 ' + (props.count + 1) + ' 次')
    }
  }
</script>
!
关于 defineEmits：

Vue 生态里另一种常见写法是 defineEmits + $emit。 官方「组件模型」文档给出的示例采用的是上面的回调函数方式， 所以本课程统一用回调写法——它有一个额外好处：参数类型写在 props 类型里，编译器能帮你检查。 如果你在别人项目里见到 defineEmits，先确认当前版本的实际行为再决定是否使用。

💡
一个命名建议：

回调名用"发生了什么"而不是"去做什么"： @onSubmit / @onChange 这种更好，父层想怎么处理由父层决定。 这能让组件真正可复用——同一个组件在 A 页面用来提交，在 B 页面用来预览，都不需要改组件。

6.5

父调子：模板 ref 与 defineExpose

20 分钟 · 讲授 + 演练

有些场景必须由父组件"主动调用子组件里的方法"，例如：页面顶部的"清空"按钮要调用表单组件的 reset()，或者"保存"时要求子组件先做一次校验。 这时需要两步：子组件用 defineExpose 暴露方法，父组件用模板 ref 拿到组件实例。

✕
官方明确说明：子组件的方法不会自动暴露给父组件。

只有通过 defineExpose 显式暴露出去的方法/数据，父组件才能通过 ref 调用。 这是很多人的第一反应会踩的坑："我明明写了 reset()，为什么父层报找不到方法？"

defineExpose + 模板 ref：页面调用组件方法 
<!-- components/signup-form/signup-form.uvue -->
<script setup>
  const name = ref<string>('')
  const phone = ref<string>('')

  const reset = () => {
    name.value = ''
    phone.value = ''
  }

  const validate = (): boolean => {
    return name.value.length >= 2 && phone.value.length == 11
  }

  // 关键：显式暴露出去，父层才调用得到
  defineExpose({ reset, validate })
</script>
<template>
  <view class="page">
    <!-- 模板 ref：ref 的名字要与下面变量名对应 -->
    <signup-form ref="formRef" />
    <button @click="onReset">清空表单</button>
  </view>
</template>

<script setup>
  // 自定义组件的实例类型是 ComponentPublicInstance
  const formRef = ref<ComponentPublicInstance | null>(null)

  const onReset = () => {
    // 拿到实例后调用被暴露出来的方法
    // （具体调用写法与类型标注以官方示例工程为准，关键是"必须 defineExpose"）
    console.log('准备调用子组件的 reset()，实例是否拿到：', formRef.value != null)
  }
</script>
<script setup>
  // 需要操作"元素"而不是"组件"时（例如测量尺寸），有两种官方方式：

  // 方式一：模板 ref + UniElement 类型
  // 
  const htmlRef = ref<UniElement | null>(null)

  // 方式二：通过 id 获取（与模板 ref 得到的是同一个元素）
  const byId = uni.getElementById('htmlRef')

  onReady(() => {
    // 注意：onLoad 阶段 DOM 还没建好，此时同步取 ref 会拿到 null
    // 要等到 onReady 之后再访问
    console.log('元素宽度：', byId?.getBoundingClientRectAsync != null)
  })
</script>

<!-- 类型规范（官方）：
     内置组件（scroll-view / slider 等）→ ref<UniSliderElement> 这类 UniXxxElement
     内置元素（view / text）        → ref<UniElement | null>
     自定义组件                     → ref<ComponentPublicInstance | null> -->
💡
能用 props / 回调解决，就不要用 ref 调方法。

ref 调方法会让父组件"知道子组件内部有什么"，耦合度更高、也更难测试。 它适合"命令式"的场景（清空、聚焦、校验、播放）， 而数据的流转仍然应该走 props 与回调。

6.6

插槽：让父组件决定"里面放什么"

15 分钟 · 讲授

props 传的是数据，插槽传的是界面片段。 当组件的外框固定、但内部内容千变万化时（例如"卡片"这个外框），插槽比 props 更合适。 官方说明组件可以封装"方法、事件、插槽"，v-slot 也在内置指令兼容清单里。

默认插槽：外框固定，内容由使用者决定 
<!-- components/app-card/app-card.uvue -->
<template>
  <view class="card">
    <text class="title">{{ title }}</text>

    <!-- 内容区交给使用者：默认插槽 -->
    <slot></slot>
  </view>
</template>

<script setup>
  const props = defineProps<{ title: string }>()
</script>

<style>
  .card { background-color: #FFFFFF; border-radius: 12px; padding: 16px; margin-bottom: 10px; }
  .title { font-size: 16px; font-weight: bold; margin-bottom: 10px; }
</style>
<template>
  <view class="page">
    <!-- 同一张卡片，装了两种完全不同的内容 -->
    <app-card title="今日课程">
      <view class="row" v-for="c in today" :key="c.id">
        <text class="name">{{ c.name }}</text>
        <text class="time">{{ c.time }}</text>
      </view>
    </app-card>

    <app-card title="快捷入口">
      <view class="grid">
        <view class="cell" v-for="m in menus" :key="m"><text>{{ m }}</text></view>
      </view>
    </app-card>
  </view>
</template>
ⓘ
关于具名插槽与作用域插槽：

官方文档确认组件支持封装插槽，v-slot 也在指令兼容清单中， 但文档没有逐条列出"具名插槽 / 作用域插槽"的限制与差异。 实践建议：先用默认插槽把"外框复用"这件事做好； 确实需要具名插槽（多个内容区）或作用域插槽（把子组件数据回传给内容）时， 对照官方示例工程（hello uvue 的组件示例）验证一次再落地。

💡
什么时候用插槽，什么时候用 props？

一句话判断：传"文字/数字/开关"用 props，传"一段界面"用插槽。 如果发现自己在用 props 传一堆标志位（showLeft / showRight / customTop）， 那通常说明这个组件应该改用插槽。

6.7

通信方式决策表 + 组件生命周期

15 分钟 · 讲授

五种通信方式，怎么选

需求方案要点
父 → 子：把数据给它显示 props 单向数据流；子组件不能改 props
子 → 父：告诉父层"发生了什么" 回调函数（父层 @callback） 官方示例采用的方式；数据仍由父层维护
父 → 子：命令它做件事（清空 / 校验 / 聚焦） ref + defineExpose 子组件必须显式暴露；能不用就不用
跨多层传递（爷爷 → 孙子） provide / inject 组合式里直接 provide('key', value)；适合"主题、当前用户"这类上下文
多个页面共享同一份状态 全局状态（store/ 目录下的响应式对象） 官方教程有专门的"全局变量与状态管理"章节；第 9 章会深入
页面之间传数据 navigateTo 的 url 参数 / event-bus 第 7 章讲
provide/inject 与全局状态（官方示例形态） 
<!-- 页面（提供方）：向下提供数据或函数，中间层不用一层层传 -->
<script setup>
  provide('msg', 'hello')
  provide('num', 0)
  provide('obj', { 'a': 1 })
  provide('arr', [1, 2, 3])
  // 也可以提供一个函数给下层调用
  provide('fn', (): string => 'hello')
</script>

<!-- 深层子组件（注入方） -->
<script setup>
  const msg = inject<string>('msg')
  const fn = inject<() => string>('fn')
</script>
// store/index.uts —— 官方"全局变量与状态管理"示例的形态
type State = {
  componentMsg: number
}

export const state = reactive({
  componentMsg: 0
} as State)

export const setComponentMsg = (value: number) => {
  state.componentMsg = value
}

组件生命周期：和页面不是一套

想做的事组件里写（组合式）说明
组件挂载完成后（可以取元素尺寸了）onMounted(() => {})对应选项式的 mounted
组件卸载前（清理定时器、取消监听）onBeforeUnmount(() => {})对应 beforeUnmount
组件已卸载后onUnmounted(() => {})对应 unmounted
"创建时"要做的事直接写在 <script setup> 顶层对应选项式的 created；注意它在组件实例化时就执行
页面加载 / 显示组件里不能直接用onLoad / onPageShow 属于页面；组合式组件可以监听所在页面的生命周期（见 6.1）
✓
一条能避免 90% 组件 bug 的规则：

组件只负责"显示 + 通知"，不负责"决定数据怎么变"。 凡是"改数据"的动作，都通过回调交给父层或全局状态去处理。 这样组件才可能被复用到第二个页面——否则第一次复用就会牵出一串连锁修改。

📌 今天你学到的，浓缩成 6 句话

组件不需要在 pages.json 注册，也不支持页面生命周期，但有自己的一套组件生命周期； 符合 组件名/组件名.uvue 规范并放在 components/ 或 uni_modules 下，就能被 easycom 自动引入， 同名时 .uvue 优先； 父传子用 props（withDefaults 给默认值），组合式用点操作符访问，子组件不要改 props； 子传父用回调函数（父层 @callback="fn"，子组件把函数声明为 props 并调用）， 数据仍然由父层维护； 父要调子组件的方法，必须子组件 defineExpose + 父层模板 ref； 没声明成 props 的属性会透传到单根节点组件的根节点上（这也是改组件外框样式的方式）； 跨多层用 provide / inject，多页面共享用全局状态，组件本身只该"显示 + 通知"。

组件 ≠ 页面 无需注册 easycom 规范 .uvue 优先 defineProps withDefaults 单向数据流 attrs 透传 inheritAttrs 回调函数 模板 ref defineExpose UniElement 插槽 provide / inject 组件生命周期

模式选型指南：蒸汽模式 / VDOM + UTS / 原生插件

uni-app x 目前有两条技术路线（蒸汽模式、VDOM 模式），以及三种扩展能力（内置组件与 API、纯 JS 库、uts 插件）。 选错的代价是"写到一半发现某能力不支持"或"老项目升级踩坑"。 这一页把它们的分工、门槛与升级路径讲清楚，并如实列出官方文档中已知的矛盾与未确认项——这一点对做技术决策同样重要。

C.1

先看清两条路线：蒸汽模式 vs VDOM 模式

10 分钟 · 讲授
对比项蒸汽模式（本课程主线）VDOM 模式（历史路线）
用什么写 标准 Vue + TS/JS + CSS 子集（与 Web 开发一致） UTS（基于 TS 的强类型语言）+ Vue
script 语言 HBuilderX 5.31 前：不要手写 lang（统一走 uts2js，强行设成 ts/js 反而可能触发问题）；
5.31+：可写 uts / ts / js，不写则取 manifest.json 的全局配置，默认是 ts		 只能是 lang="uts"
类型要求 运行在 JS 环境，不再要求强类型（TS 类型仅开发期生效，运行期被擦除） Android 端按 uts2kt 执行时要求强类型
API 写法限制 仅支持组合式 API，不支持选项式与 mixin 组合式与选项式可混用
样式隔离 仅支持样式隔离策略 2.0 默认老策略，需在 manifest.json 里配 uni-app-x.styleIsolationVersion: "2" 才启用 2.0
特殊类型 没有 UTSJSONObject 专有方法，type 会被擦除 UTSJSONObject 支持 getString / getNumber / getArray 等专有方法；type 会编译成 class；部分内置 API 的 undefined 被改为 null
渲染性能 视图层（template + style）在编译期静态分析，编译为高度优化的机器码/字节码，官方 benchmark 显示渲染优于原生实现 存在 VDOM 开销，官方对比中慢于蒸汽模式
编译到 Web / 小程序 注意：蒸汽模式编译到 Web / 小程序端时，目前仍按 VDOM 模式运行——这两端的运行特性与 App 端会有差异，调试时别混淆
ⓘ
为什么本课程主线选蒸汽模式？

① 对你们的知识结构最友好：已经会 H5/CSS3/JS，蒸汽模式用的就是 Vue + TS + CSS 子集，几乎不需要再学一门语言； ② 官方推荐新项目使用，且 5.25+ 新建工程默认就是蒸汽模式； ③ 性能路线更优（编译期静态分析 + 机器码/字节码）； ④ AI 工具与生态支持更好（官方明确说明蒸汽模式对 AI 更友好）。 代价是：Uts 插件开发仍然需要 UTS——所以我们在第 10 章会讲清"什么时候必须碰 UTS"。

C.2

版本与平台门槛：先确认"能不能跑"

10 分钟 · 讲授

做技术选型，第一步永远是确认门槛。下面这些数字会直接决定"你的目标用户装得上吗"。

项目蒸汽模式VDOM 模式
HBuilderX 起始版本鸿蒙 5.0、iOS 5.11、Android 5.21更早的版本即支持（uni-app x 初代路线）
最低系统版本Android 6+、iOS 15+、鸿蒙 API20+Android 5+、iOS 12+、鸿蒙 API14+
Web 端运行环境发行模式最低 Chrome 64 / Safari 11.1 / Firefox 62 / Edge 79；运行模式最低 Chrome 66
媒体查询适配暗黑模式App 端需 HBuilderX 5.25+不支持（需用监听 + 动态 class）
页面默认可滚动HBuilderX 5.12+ 起页面默认可滚动（要禁用就配 disableScroll）不同
!
选型时最容易被忽略的一句：

如果你的课程项目要交给同学安装体验，请写明最低系统要求。 "iOS 15+"意味着 iPhone 6s 之后的机型基本都可以，但更老的设备装不上； "Android 6+"覆盖面很广，基本没有障碍。 这类"非技术"的约束，往往是汇报时被问到却答不上来的那一类问题。

C.3

要一个能力时：内置 → JS 库 → uts 插件

15 分钟 · 讲授

当你想实现某个功能时，按下面顺序找答案，越靠前越省事：

顺序方式适用成本
① 官方内置组件与 API 绝大多数需求：网络、存储、相机相册、扫码、定位、剪贴板、系统信息、弹窗…… 最低。先查官方组件/API 清单，八成能直接找到
② 插件市场 / uni_modules 官方没内置、但别人封装好的能力（UI 库、图表、原生 SDK 桥接） 低。安装即用；需确认插件是否声明支持 uni-app x 与蒸汽模式
③ 纯 JS/TS 库（npm） 纯逻辑库：日期处理、工具函数、状态管理 低。蒸汽模式下纯 JS 库通常可直接用于 App 平台；但依赖 window / document 的库不可用
④ uts 插件（含原生混编） 调用某个平台的专属能力、对接第三方原生 SDK、需要强类型跨端一致 最高。需要写 UTS，可能要写 Kotlin/Swift/ArkTS 混编
💡
一句话判断"要不要写 UTS"：

如果这个能力某个平台的原生代码里有、而 uni 的跨端 API 里没有，才需要 UTS 插件。 例如：读取某些系统级传感器、对接厂商推送 SDK、调用某个银行/支付 SDK。 反过来，"获取定位""扫码""选择相册"这类高频需求官方都已内置，不需要写 UTS。

C.5

老项目升级：从 uni-app / VDOM 到蒸汽模式

15 分钟 · 讲授

现实项目里你更可能遇到的是"维护一个老项目"。官方给出了升级指南与转换思路， 下面把它整理成可以照着做的步骤。

阶段要做什么怎么判断做完了
① 先跑起来 用新版 HBuilderX 打开工程，先让它能编译运行，不要一上来就改代码 能在浏览器或真机上打开首页
② 选项式 → 组合式 data / methods / 生命周期改写成 <script setup> 组合式； 页面 onShow / onHide 改成 onPageShow / onPageHide； mounted / unmounted 改成 onMounted / onUnmounted； mixin 拆成普通函数 不再出现 export default {}；mixin 已清零
③ 处理类型与 UTSJSONObject 蒸汽模式里 UTSJSONObject 的专有方法（getString / getNumber / getArray）不可用， 改成普通对象的点号访问；JSON.parseArray / parseObject 改用 JSON.parse； 需要保留 UTS 行为时，把该页面的 lang 显式指定为 uts 控制台不再报 getString is not a function 这类错误
④ 处理样式与选择器 把 .parent .child 这类复杂关系选择器改成明确的 class 命名（推荐 BEM 风格）； 检查组件样式隔离假设是否还成立 真机界面与升级前一致
⑤ 检查组件与列表 list-view / list-item 的循环必须有稳定 :key； list-item 内文本用 text 包裹；布尔属性显式写 true / false，不依赖旧默认值 长列表滚动正常、无复用错位
⑥ 真机回归 逐个平台验证：浏览器、Android、iOS、鸿蒙、小程序（按你的发布范围） 每个目标端都能完成主流程
ⓘ
官方在这里给了两个很实用的"AI 提示词"：

官方「uvue 概述」文档中直接给出了两段提示词模板：一段用于"选项式 → 组合式"改造， 一段用于"适配蒸汽模式"。它们的写法值得学习，因为它们把"不许改业务逻辑、 不许漏代码与注释、改完必须自己看编译报错并修到无错"这些约束都写进了提示词里。 这其实也是你以后写 AI 提示词的最佳模板。

💡
给课程项目的建议：

学期内的小项目不要做"全量升级"这种高风险动作。 如果要用老项目练手，选一个页面升级、写清"改了什么、为什么、遇到什么坑"， 这比"升级了整个项目但说不清"得分更高。

C.6

如实列出：官方文档中已知的矛盾与未确认项

10 分钟 · 讲授

技术选型必须建立在"我知道自己不知道什么"之上。下面这些点，是本课程在核对官方文档时 发现存在矛盾、或文档未明确给出的地方。它们不代表框架有问题（版本迭代快的框架都会有这类情况）， 但写进项目之前请自己验证一次。

项目官方表述情况建议做法
calc() 矛盾：CSS 方法页把它列入 App 支持清单，但 position 页示例注释写着"App 端暂不支持 calc" 避免用 calc() 组合安全区变量；需要额外间距用 margin / padding
position: sticky 矛盾：同一页的"App 平台差异"写不支持 sticky，属性值表里又列出了 sticky 需要吸顶效果时，优先用官方提供的 sticky 组件或改用其他布局方案
蒸汽模式的关系选择器 矛盾：一处说"只支持简单 class 选择器与分组选择器"，另一处说"分组/子代/后代/兄弟选择器暂不支持" 统一只用单一 class（本课程第 1、3 章的口径），最稳且不影响表达力
tabBar 的 midbutton 矛盾：pages.json 文档说"不再支持 tabbar 的 midbutton"，但 API 目录里存在"监听中间按钮点击"的页面 不要依赖它；需要中间凸起按钮就用扩展组件（如 uni-ui x 的 tab-bar）
vh / vw 未确认：官方长度单位文档只列了 px、rpx 与百分比 撑满用 flex: 1，比例用百分比；非要用 vh/vw 就先真机验证
页面栈层数上限 / navigateBack 的多层返回参数 未确认：本次核对时相应页面内容被截断，未见明确数值与字段 不要造"无限跳转"的页面链；需要回到起点用 reLaunch
button 的 open-type 完整取值、input 的 @confirm 事件细节 未确认：部分表格由脚本注入，核对时未取全 用到这些能力时，直接查官方组件页当前版本表格
✓
这件事的真正意义，比"记住这七条"更重要：

当你在真实工作里看到"文档 A 说可以、文档 B 说不可以"时，正确的做法不是选一个信、也不是放弃， 而是写 10 行代码在目标平台验证一次，并把结论记进团队文档。 这类"验证并沉淀"的能力，恰好是初级与中级工程师之间最明显的分界线。 本课程附录 B 给你准备了排错笔记模板，可以直接用来记录这类结论。

答辩时一定会被问"为什么这么选"
ⓘ
本课程的选型结论（可直接引用，但要说明前提）：

主线：蒸汽模式（Vue + TS/JS + ucss）+ 官方内置组件与 API + 需要时用 uni_modules 插件； 仅当目标平台有专属能力需求时才写 uts 插件。 前提假设是：面向大学生的教学项目、以 App 与 Web 为主要发布端、不涉及复杂的第三方原生 SDK。 如果你的项目不满足这些前提，请按 C.4 的决策器重新判断。

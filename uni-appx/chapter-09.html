本地存储与全局状态管理：数据该住在哪里

第 8 章解决了"怎么把数据拉回来"，这一章解决"拉回来之后放哪儿"。 很多项目的混乱都源于这件事没想清楚：同一个数据在三个页面各存了一份、改了一个另两个不更新、 用户清了缓存登录态就丢。 本章给你一套清晰的判断标准，以及两个最常用机制：本地存储与全局状态。

9.1

先分类：数据该住在哪里

10 分钟 · 讲授

数据只有三个可能的位置，选错了就会带来一连串麻烦。 判断方法是问两个问题：它需要跨页面共享吗？它需要在"关掉 App 再打开"之后还在吗？

位置丢失时机适合放什么不适合放什么
① 组件内部状态
（ref / reactive）		 页面/组件销毁就没了 只在本页面用、且不需要恢复的数据：输入框内容、当前 tab、展开状态 需要跨页面共享或重启后仍在的数据
② 全局状态
（store/ 下的响应式对象）		 App 进程结束就没了 多个页面都要读、且需要实时同步的数据：当前用户信息、购物车、未读数、主题设置 海量数据（列表全量缓存）、敏感密钥
③ 本地存储
（uni.setStorageSync 等）		 用户清数据/卸载才没（App 端持久化） 重启后仍要恢复的"小数据"：token、用户偏好、草稿、收藏 id 列表、上次同步时间 大数据、需要频繁读写的高频数据（它没有响应式能力）
ⓘ
最容易被搞混的一组关系：全局状态 ≠ 本地存储

全局状态解决的是"多个页面读到同一份、改了一处别处自动更新"（响应式共享）； 本地存储解决的是"App 关掉再打开还在"（持久化）。 它们职责不同，所以成熟项目里常见组合是： 启动时从存储里读出 token 放进全局状态 → 各页面读全局状态 → 修改时同时写回存储。 这也是本章最后要落地的模式。

💡
一条能避免 80% 数据混乱的规则：

同一份数据全项目只允许有一个"真值来源"。 如果 token 既存在存储里、又存在全局状态里、页面里还各存一份， 那你迟早会遇到"某处显示已登录、实际请求已被拒绝"这类难查的问题。

9.2

本地存储 API：同步与异步成对出现

20 分钟 · 讲授 + 演练

官方存储接口都以"同步 + 异步"成对提供。同步版写起来短，异步版不阻塞。

用途同步写法异步写法
写入 / 覆盖uni.setStorageSync(key, data)uni.setStorage({ key, data, success, fail })
读取uni.getStorageSync(key)uni.getStorage({ key, success, fail })
删除某个 keyuni.removeStorageSync(key)uni.removeStorage({ key, ... })
清空全部uni.clearStorageSync()uni.clearStorage({ ... })
查看占用情况uni.getStorageInfoSync()uni.getStorageInfo({ success })
utils/storage.ts —— 一个带类型的存储小工具 
// 存储 key 统一在这里登记，避免各处拼字符串写错
const KEY_TOKEN = 'app_token'
const KEY_USER = 'app_user'
const KEY_DRAFT = 'app_draft'

/* ---------- 读：注意同步版读不到时返回的是"空字符串" ---------- */
export const getString = (key: string): string => {
  const v = uni.getStorageSync(key)
  // getStorageSync 返回 any：必须 as 成正确类型才能当字符串用（见 9.4）
  return v as string
}

export const getObject = <T>(key: string): T | null => {
  const raw = uni.getStorageSync(key) as string
  if (raw.length == 0) return null          // 同步版读不到 → 空字符串
  try {
    return JSON.parse(raw) as T
  } catch (e) {
    console.log('本地缓存解析失败：', key, e)
    return null                             // 缓存脏了就当没有，不要崩
  }
}

/* ---------- 写：只支持能被 JSON.stringify 序列化的数据 ---------- */
export const setObject = (key: string, value: any) => {
  uni.setStorageSync(key, JSON.stringify(value))
}

/* ---------- 删 ---------- */
export const remove = (key: string) => {
  uni.removeStorageSync(key)
}

/* ---------- 查看占用（currentSize / limitSize 单位是 kb） ---------- */
export const storageInfo = () => {
  const info = uni.getStorageInfoSync()
  console.log('已用：', info.currentSize, 'KB / 上限：', info.limitSize, 'KB')
  console.log('所有 key：', info.keys.join('、'))
}

export { KEY_TOKEN, KEY_USER, KEY_DRAFT }
!
同步版与异步版有两个关键差异，必须记住：

① 读一个不存在的 key：同步版 getStorageSync 返回空字符串（不是 null， 所以"没存过"和"存了空字符串"分不出来）；异步版 getStorage 会触发 fail 回调 （错误信息 getStorage:fail data not found）。 需要严格区分时用异步版。 ② 数据量大时用异步——官方明确建议：获取较大量的数据时用 uni.getStorage，避免同步阻塞。

✕
key 命名有一条硬规则：

uni-、uni_、dcloud-、dcloud_ 是系统保留前缀 （例如 uni_deviceId、uni_id_token）。 自己起名时请避开这些前缀，用项目自己的前缀更安全，例如 app_token、app_user。

9.3

平台差异：同一行代码，三种命运

15 分钟 · 讲授

存储是"跨端差异最明显"的一块。官方把各平台的实现说得很清楚， 而这些差异直接决定了"你的缓存策略在某个平台上会不会翻车"。

平台底层实现容量与生命周期对你的影响
Web / H5 浏览器的 localStorage 约 5MB 上限；官方明确它"是缓存概念，可能会被清理" 不能把"唯一一份"关键数据只放在这里；用户清浏览数据就没了
App（Android / iOS） 原生 storage（Android 端是应用内 SQLite） 无大小限制，不是缓存，是持久化的 可以放心存 token、草稿；但仍要自己控制体积（别把整张图片塞进去）
微信小程序 小程序自带 storage 单个 key 最大 1MB，全部数据上限 10MB 存大对象（如长列表）很容易撞上限
支付宝小程序 小程序自带 storage 单条转字符串后最大 200×1024 字符，总量上限 10MB 同上，且单条限制更紧
!
一个很少人知道、但很致命的注意点：

官方说明：非 App 平台清空 Storage 会导致 uni.getSystemInfo / getDeviceInfo 获取到的 deviceId 改变。 也就是说，如果你在 Web 或小程序上调用 clearStorageSync()， 设备标识可能会变——凡是拿 deviceId 做"用户唯一标识 / 免登录 / 数据绑定"的逻辑都会受影响。 结论：不要动不动就"清空全部"，删除自己用到的 key 就好。

💡
听到"缓存"两个字，先问一句：

"丢了会怎样？" 丢了无所谓 → 可以缓存在本地，过期就重新拉； 丢了会出事（登录态、用户数据、未提交的草稿）→ 要在服务端有备份，本地只是加速。 把这句话问清楚，缓存策略就不会设计错。

9.4

序列化与类型：两个必踩的坑

15 分钟 · 讲授
坑官方说明正确做法
存进去的东西有类型限制 data 类型是 any，但"只支持能通过 JSON.stringify 序列化的对象" 对象统一 JSON.stringify 后再存（本项目用 setObject 包了一层）；
函数、循环引用的对象存不了；日期会被转成字符串，取出后要自己转回
取出来是 any getStorageSync 返回值类型是 any，"使用 any 类型的数据需要 as 为正确的类型， 才能调用类型上的方法" 取出后立刻断言：字符串 as string；对象先 as string 再 JSON.parse 并 as T； 复杂类型（UTSJSONObject / type / class）的取法见官方"获取复杂类型的数据"章节
同步读不存在的 key 返回空字符串 官方明确：同步方法返回空字符串而不是 null；要区分空字符串与 null 请用异步方法 用 raw.length == 0 作为"没有缓存"的判断；需要精确区分时改用异步 uni.getStorage 的 fail 分支
同一个数据的"存"与"取"（对照着看） 
type User = { 'id': number, 'name': string }

const user: User = { 'id': 1, 'name': '汽水同学' }

// ❌ 直接存对象：官方要求"只支持能通过 JSON.stringify 序列化的对象"，
//    显式序列化更可控，也便于以后换存储方案
// uni.setStorageSync('app_user', user)

// ✅ 统一序列化后再存
uni.setStorageSync('app_user', JSON.stringify(user))

// 字符串直接存即可
uni.setStorageSync('app_token', 'eyJhbGciOi...')

// 布尔、数字也可以存（它们本身可序列化）
uni.setStorageSync('app_dark_mode', true)
// ① 字符串：直接断言
const token = uni.getStorageSync('app_token') as string
if (token.length > 0) {
  console.log('已登录')
}

// ② 对象：先断言成字符串，再 JSON.parse，再断言成目标类型
const raw = uni.getStorageSync('app_user') as string
if (raw.length > 0) {
  const user = JSON.parse(raw) as User
  console.log(user.name)
}

// ③ 布尔
const dark = uni.getStorageSync('app_dark_mode') as boolean

// ④ 拿不准时先看类型：调试期很有用
console.log('实际类型：', typeof uni.getStorageSync('app_user'))
// 日期没有"原样存储"这回事：JSON.stringify 会把它变成 ISO 字符串
const now = new Date()
uni.setStorageSync('app_last_sync', now.toISOString())     // 存字符串最稳

// 取出来自己转回
const iso = uni.getStorageSync('app_last_sync') as string
if (iso.length > 0) {
  const t = new Date(iso)
  console.log('上次同步：', t.toLocaleString())
}

// 更推荐：直接存时间戳（number），比较大小最方便
uni.setStorageSync('app_last_sync_ts', now.getTime())
const ts = uni.getStorageSync('app_last_sync_ts') as number
✓
经验：把 JSON.parse 包在 try / catch 里。

本地缓存是"可能变脏"的：用户可能在旧版本 App 里存过结构不同的数据， 或存储被外部修改。解析失败时最稳的处理是当作没有缓存并重新请求， 而不是让整个页面崩掉——上面 getObject 的写法就是这个思路。

9.5

全局状态：给跨页面数据一个家

20 分钟 · 讲授 + 演练

场景：首页右上角显示未读消息数，"我的"页面也能看到同一个数字，用户点进消息页读完后， 两个地方都要立刻减少。用 props 一层层传？用事件总线广播？用本地存储？ 都不合适——这时候需要全局状态。

官方在"组件模型"与"全局变量与状态管理"教程里给出的形态是： 在 store/ 目录下导出一个响应式对象，配套导出修改它的函数。

store/index.uts —— 官方示例形态的全局状态 
// store/index.uts
type State = {
  isLogin: boolean,
  userName: string,
  unread: number
}

// reactive：整个对象都是响应式的，任何页面读它、改它都会同步
export const state = reactive({
  'isLogin': false,
  'userName': '',
  'unread': 0
} as State)

// 推荐：修改统一走函数，而不是让每个页面直接改 state
export const setLogin = (name: string) => {
  state.isLogin = true
  state.userName = name
}

export const logoutState = () => {
  state.isLogin = false
  state.userName = ''
  state.unread = 0
}

export const setUnread = (n: number) => {
  state.unread = n
}
两个页面共享同一份状态（官方示例的用法） 
<script setup>
  // 页面 A：显示未读数，并提供一个"读完"的操作
  import { state, setUnread } from '@/store/index.uts'

  // 用 computed 派生，模板里直接 {{ unread }}
  const unread = computed<number>((): number => state.unread)

  const readAll = () => {
    setUnread(0)          // 改全局状态
  }
</script>

<script setup>
  // 页面 B：同一个数字，改完立刻同步（不需要任何传参或事件）
  import { state } from '@/store/index.uts'

  const unread = computed<number>((): number => state.unread)
</script>
ⓘ
为什么"修改统一走函数"？

① 改数据的地方集中，出问题好查； ② 可以在函数里顺手做"副作用"，例如写回本地存储、打日志、上报统计； ③ 页面代码只需 import 一个函数名，不用知道内部结构，将来重构不影响页面。 这和你在第 4 章学的"组件只负责显示与通知"是同一种思路。

!
全局状态不是"什么都能往里塞"：

只放真正跨页面共享、且需要实时同步的数据（登录态、用户信息、未读数、主题、购物车）。 单个页面自己的状态（当前 tab、输入框内容、列表数据）应该留在页面里。 把一切塞进全局，会让"这个数据什么时候被谁改了"变得无法追踪——这是项目后期最难治的病之一。

9.6

实战：登录态的完整生命周期

25 分钟 · 全程动手

登录态是最典型的"存储 + 全局状态 + 请求"三者联动场景。把它讲清楚，你就掌握了本章的全部要点。 它的生命周期只有五步：

步骤做什么用本章的哪个能力
① 登录成功拿到 token 与用户信息，存本地 + 写入全局状态存储 API + store
② 每次请求把 token 放进请求头 Authorization第 8 章的请求封装
③ 启动恢复App 重开时从存储读出 token，恢复登录态存储读取（放在页面 onLoad 或 App.uvue）
④ 失效处理接口返回 401 时清理登录态并统一跳登录页store 的 logoutState() + reLaunch
⑤ 主动退出清理 token、重置全局状态、回到登录页同上
utils/auth.ts —— 登录态统一出入口 
// utils/auth.ts
import { setLogin, logoutState } from '@/store/index.uts'

const KEY_TOKEN = 'app_token'
const KEY_USER = 'app_user'

/* ---------- ① 登录成功后保存 ---------- */
export const saveLogin = (token: string, user: UserInfo) => {
  uni.setStorageSync(KEY_TOKEN, token)                 // 持久化
  uni.setStorageSync(KEY_USER, JSON.stringify(user))
  setLogin(user.name)                                  // 同步全局状态
}

/* ---------- ② 请求头里取 token（供请求封装调用） ---------- */
export const getToken = (): string => {
  return uni.getStorageSync(KEY_TOKEN) as string
}

/* ---------- ③ 启动时恢复登录态 ---------- */
export const restoreLogin = () => {
  const token = getToken()
  if (token.length == 0) return false

  const raw = uni.getStorageSync(KEY_USER) as string
  if (raw.length > 0) {
    try {
      const user = JSON.parse(raw) as UserInfo
      setLogin(user.name)
    } catch (e) {
      console.log('用户信息解析失败，按未登录处理')
      clearLogin()
      return false
    }
  }
  return true
}

/* ---------- ④⑤ 失效与退出：清理并回登录页 ---------- */
export const clearLogin = () => {
  uni.removeStorageSync(KEY_TOKEN)      // 只删自己的 key，不要 clearStorage
  uni.removeStorageSync(KEY_USER)
  logoutState()
}

export const gotoLogin = () => {
  // 用 reLaunch：清空页面栈，用户不能再"返回"到需要登录的页面
  uni.reLaunch({ 'url': '/pages/login/login' })
}
在请求封装里接上 401 统一处理（第 8 章的 request 升级） 
// utils/request.ts 的关键片段
'header': {
  'Content-Type': 'application/json',
  'Authorization': 'Bearer ' + getToken()          // ← 自动带上 token
},
'success': (res) => {
  if (res.statusCode == 401) {                     // ← HTTP 层未授权
    clearLogin()
    gotoLogin()
    resolve(null)
    return
  }
  if (res.statusCode != 200) { /* ... */ }

  const body = res.data as UTSJSONObject
  if ((body['code'] as number) == 401) {           // ← 业务码未授权
    clearLogin()
    gotoLogin()
    resolve(null)
    return
  }
  // ...
}
✕
三个安全与体验上的红线：

① 不要把密码存进本地存储——存 token 就够了，而且 token 应该有有效期； ② 不要用 clearStorageSync() 来"退出登录"——它会清掉草稿、收藏等无关数据， 在非 App 平台还可能改变 deviceId（见 9.3）； ③ 失效时要跳转登录页并清空页面栈（reLaunch）， 否则用户会停留在"需要登录才能看"的页面上反复报错。

9.7

缓存策略：先缓存后请求

15 分钟 · 讲授

第 8 章我们提过"离线优先"。现在有了存储能力，可以把它落地成一套清晰的策略：

带过期时间的缓存读取（列表页首屏） 
<script setup>
  import { request } from '@/utils/request'

  type CacheBox = { ts: number, rows: Notice[] }

  const CACHE_KEY = 'app_notice_list'
  const MAX_AGE = 5 * 60 * 1000         // 5 分钟：超过就认为过期

  const list = ref<Notice[]>([])

  const readCache = (): Notice[] => {
    const raw = uni.getStorageSync(CACHE_KEY) as string
    if (raw.length == 0) return []
    try {
      const box = JSON.parse(raw) as CacheBox
      if (Date.now() - box.ts > MAX_AGE) return []      // 过期就当没有
      return box.rows
    } catch (e) {
      return []
    }
  }

  const writeCache = (rows: Notice[]) => {
    const box: CacheBox = { 'ts': Date.now(), 'rows': rows }
    uni.setStorageSync(CACHE_KEY, JSON.stringify(box))
  }

  const load = async () => {
    // 第一步：先用缓存渲染，用户立刻看到内容（而不是转圈）
    const cached = readCache()
    if (cached.length > 0) list.value = cached

    // 第二步：再请求最新数据并覆盖
    const rows = await request<Notice[]>({ 'url': '/notices', 'showError': cached.length == 0 })
    if (rows != null) {
      list.value = rows
      writeCache(rows)                  // 成功才写缓存
    }
  }

  onLoad(() => { load() })
</script>
问题建议做法
缓存什么？列表首屏数据、用户信息、字典/配置这类"读多写少"的数据；不要缓存别人的隐私数据
缓存多久？给每个缓存带时间戳（或用 key 里带日期）；列表类 1–5 分钟，配置类可长一些，登录态由服务端有效期决定
什么时候写？只有请求成功才写。失败时保留旧缓存，比清空更友好
缓存多大？只存"首屏要用的那一页"，别把整个列表/图片塞进去（小程序单 key 只有 1MB）
什么时候清？退出登录时清与用户相关的缓存；提供"清除缓存"入口时用 removeStorageSync 逐个删，别用 clearStorageSync
💡
一个能立刻提升体验的小技巧：

数据分三处住：页面状态（用完就丢）/ 全局状态（跨页面实时共享）/ 本地存储（重启后还在）， 同一份数据只能有一个真值来源； 存储 API 同步异步成对：setStorageSync / getStorageSync / removeStorageSync / getStorageInfoSync， 同步读不存在的 key 返回空字符串（不是 null），异步读会走 fail，大批量数据优先用异步； 平台差异很大：H5 只有约 5MB 且属于可能被清理的缓存，App 是持久化且无大小限制，小程序单 key 1MB / 总量 10MB； key 要避开 uni- / uni_ / dcloud- / dcloud_ 保留前缀， 并且在非 App 平台清空 Storage 会改变 deviceId，所以别用 clearStorageSync 做"退出登录"； 存储里取出的值是 any，必须 as 成正确类型（对象要 as string 后再 JSON.parse，并包 try/catch）； 跨页面共享状态用 store/index.uts 里的 reactive 对象 + 修改函数， 登录态走完"保存 → 带请求头 → 启动恢复 → 401 清理并 reLaunch"五步，缓存做到"先缓存后请求、成功才写、带过期时间"。

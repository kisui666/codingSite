响应式数据与模板语法：把界面交给数据

第 1 章我让你记住一句话：改数据，不改界面。这一章要把这句话落到具体代码上—— 什么时候用 ref、什么时候用 reactive、什么时候该写 computed、 watch 又该用在哪；以及模板里到底能写什么、不能写什么。 这一章学扎实，第 5–12 章的交互代码都会变得顺理成章。

4.1

心智模型：从"操作元素"到"描述状态"

15 分钟 · 讲授 + 对比

先看同一件事在 Web 与 uni-app x 里的两种写法。需求：点击按钮，把页面上的数字 +1。

同一个需求，两种思维 
// ① 先定义"要操作哪个元素"，并维护一份中间数据
let count = 0
const el = document.getElementById('num')

// ② 数据变了之后，还得记得"手动把界面同步一遍"
const add = () => {
  count = count + 1
  el.textContent = String(count)     // ← 忘写这一行，界面就不会变
}

// ③ 界面上一旦多出几处用到 count，就要多维护几处同步代码
<script setup>
  // ① 只声明"状态是什么"
  const count = ref(0)

  // ② 只改状态，不关心界面
  const add = () => {
    count.value = count.value + 1
  }
</script>

<template>
  <!-- ③ 界面声明"它要显示 count"，数据一变自动更新 -->
  <text>{{ count }}</text>
  <button @click="add">+1</button>
</template>
ⓘ
两种思维的本质差别：

命令式：你告诉程序"怎么做"——找到元素、改它的内容、记住改了几次。 声明式：你只描述"状态是什么"和"界面应该长什么样"，框架负责把两者同步。 代价是你要开始认真思考：哪些数据是"状态"，哪些只是"算出来的结果"——这正是本节要建立的分类。

三分类：状态、派生、副作用

写交互代码时，任何一份数据都可以归到下面三类之一。分类错了，代码就会又长又容易出 Bug。

类别含义用什么典型例子
状态（源数据） 由用户操作或接口返回直接改变的"原始数据" ref / reactive 输入框内容、当前页码、已选中的标签、接口返回的列表
派生数据 完全由其它状态算出来的结果，不需要单独维护 computed 过滤后的列表、总条数、合计金额、"是否可提交"的布尔值
副作用 状态变化后需要"对外做点事"，而不是产生新数据 watch 关键词变化后发请求、表单变化后写缓存、数据变化后打日志
💡
一个判断口诀：

"能不能算出来？"能算出来的，就不要单独存一份（用 computed）； 算不出来的才是状态（用 ref）； 变化之后要"顺便做点别的事"，才用 watch。 新手最常犯的错，是把"能算出来的东西"也存成状态，然后费力地到处同步它。

4.2

ref 与 reactive：状态怎么声明

25 分钟 · 讲授 + 演练

在 uni-app x 里，Vue 的公开 API 全部由编译器自动引入，不需要写 import—— ref、reactive、computed、watch、onMounted、onLoad 都是直接可用。 这也是为什么你在前面的示例里从没见过 import { ref } from 'vue'。

pages/demo/state.uvue —— ref 的三种写法 
<script setup>
  // ① 简单值：让编译器自行推导
  const count = ref(0)

  // ② 推荐：显式写上类型，数组与对象必须写元素类型
  const keyword = ref<string>('')
  const list = ref<Notice[]>([])

  // 类型别名放在使用之前，读代码的人一眼就知道数据结构
  type Notice = {
    id: number,
    title: string,
    done: boolean
  }

  // ③ 事件处理函数推荐用箭头函数：
  //    官方说明普通 function 在不同平台的作用域有细微差异，箭头函数更稳
  const add = () => {
    count.value = count.value + 1        // 脚本里读写都要带 .value
  }

  const clear = () => {
    keyword.value = ''                   // 字符串同理
    list.value = []                      // 数组整体赋值，比原地修改更可靠
  }
</script>
!
关于 .value 的唯一规则：

在 <script> 里必须写 .value；在 <template> 里不要写。 模板会自动解包，所以你写 {{ count }} 而不是 {{ count.value }}。 忘记在脚本里写 .value 是初学者最高频的错误，症状是"数字没变化、列表没更新"。

reactive：适合"一组互相关联的状态"

当一个页面里有一组总是一起出现的数据（比如用户信息、表单的多个字段），用 reactive 会更清爽： 它把整个对象变成响应式，访问属性时不写 .value。

reactive 的官方写法（含类型断言） 
<script setup>
  type UserState = {
    name: string,
    level: number,
    tags: string[]
  }

  // 官方示例的写法：对象后面用 as 断言类型
  const user = reactive({
    'name': '汽水同学',
    'level': 3,
    'tags': ['前端', '移动开发']
  } as UserState)

  // 改属性：不用写 .value
  const levelUp = () => {
    user.level = user.level + 1
  }

  const addTag = (tag: string) => {
    user.tags = user.tags.concat(tag)     // 整体赋值，最稳
  }
</script>
✕
不要解构 reactive：

const { name } = user 这种写法会把响应式丢掉——之后你再改 user.name， 界面上的 name 不会跟着变。正确做法是始终用 user.name 这样带对象前缀的方式访问。 如果你发现自己很想解构，通常说明这个对象该拆成几个 ref 了。

场景推荐原因
数字、字符串、布尔值ref简单直接，赋值即更新
数组（列表、结果集）ref<T[]>([])整体替换最可靠；类型标注清楚
一组互相关联的字段（用户信息、表单）reactive少写 .value，语义更像"一个实体"
需要在多个页面/组件共享的状态抽到独立文件里导出第 9 章会把它升级成正式的全局状态方案
4.3

computed 与 watch：算出来的，和顺便要做的

25 分钟 · 讲授 + 演练

computed：别在模板里做计算

下面这段代码能跑，但它是坏味道：模板里出现了数组的 filter 与判断逻辑。 模板应该"一眼看出界面长什么样"，而不是承担业务计算。

用 computed 把计算从模板里拿出来 
<!-- 模板里做过滤：每次重渲染都要重算，逻辑也不好复用 -->
<template>
  <view v-for="item in list.filter((x) => x.title.includes(keyword))" :key="item.id">
    <text>{{ item.title }}</text>
  </view>
</template>
<script setup>
  type Notice = { id: number, title: string, done: boolean }

  const keyword = ref<string>('')
  const list = ref<Notice[]>([])

  // 派生数据：由 keyword 与 list 算出来，不需要单独维护、也不会忘记同步
  const filtered = computed<Notice[]>(() => {
    if (keyword.value.length == 0) return list.value
    return list.value.filter((item) => item.title.includes(keyword.value))
  })

  // 再派生一层也很自然：数量由 filtered 算出来
  const total = computed(() => filtered.value.length)
  const doneCount = computed(() => filtered.value.filter((item) => item.done).length)
</script>

<template>
  <!-- 模板只负责展示 -->
  <view v-for="item in filtered" :key="item.id">
    <text>{{ item.title }}</text>
  </view>
  <text>共 {{ total }} 条，已完成 {{ doneCount }} 条</text>
</template>
ⓘ
computed 和"普通函数"的区别：

写成 const filtered = () => {...} 然后在模板里 filtered() 调用也能跑， 但这样每次重渲染都会重新执行一遍。 computed 会记住上次的结果，只有它依赖的数据变了才重新计算—— 页面越复杂，这个差别越明显。

watch：状态变化后"顺便做点别的事"

watch 不产出新数据，它用来触发副作用。最典型的两个场景： 输入变化后延迟发请求（防抖搜索）、数据变化后写入本地缓存。

watch 实战：搜索防抖 + 缓存 
<script setup>
  const keyword = ref<string>('')
  const logs = ref<string[]>([])
  let timer: number | null = null            // 防抖用的定时器

  // 关键词变化 → 等 400ms 没有新输入，才真正去"搜索"
  watch(keyword, () => {
    if (timer != null) clearTimeout(timer)   // 先取消上一次待执行的搜索
    timer = setTimeout(() => {
      const word = keyword.value
      if (word.length == 0) return
      logs.value = logs.value.concat('搜索：' + word)   // 这里换成 uni.request（第 8 章）
    }, 400)
  })

  // 列表变化 → 写入本地缓存（第 9 章会细讲存储）
  // watch(list, () => {
  //   uni.setStorageSync('notice_list', JSON.stringify(list.value))
  // })
</script>
你的需求用哪个判断依据
列表要按关键词过滤后显示computed结果是"算出来的"，不影响外部
显示"共 N 条 / 已完成 M 条"computed同上
按钮是否可点击（表单是否填全）computed布尔值也是派生数据
输入停止 400ms 后发请求watch要"对外做事"（发请求），不是算数据
数据变化后写缓存 / 打点 / 弹提示watch副作用
进入页面加载数据都不用，用生命周期这不是"数据变化触发"，而是"页面加载触发"（第 7 章）
!
两个容易踩的坑：

① 不要在 computed 里改其它状态——计算属性只应该"算"，不该"做"； ② watch 里改的状态又触发它自己会造成死循环（例如监听 A 又去改 A）。出现"页面疯狂刷新"时优先怀疑这一点。

4.4

模板语法全解：插值、动态 class / style、多根节点

25 分钟 · 讲授 + 演练

插值与表达式

{{ }} 里可以写任意表达式（能算出值的东西）：三元、字符串拼接、方法调用、数组长度等。 但不能写语句（if / for / 赋值）。

模板里能写什么、不能写什么 
<template>
  <view class="page">
    <!-- ✅ 可以：三元表达式 -->
    <text>{{ list.length > 0 ? '有 ' + list.length + ' 条通知' : '暂无通知' }}</text>

    <!-- ✅ 可以：方法调用（返回值用来显示） -->
    <text>{{ formatTime(item.createdAt) }}</text>

    <!-- ✅ 可以：可选链与空值兜底 -->
    <text>{{ user?.name ?? '未登录' }}</text>

    <!-- ❌ 不可以：语句、赋值、复杂逻辑 -->
    <!-- <text>{{ if (list.length > 0) { ... } }}</text> -->
  </view>
</template>

<script setup>
  // 需要格式化的逻辑放在函数里，模板保持干净
  const formatTime = (ts: number): string => {
    return new Date(ts).toLocaleDateString()
  }
</script>
ⓘ
模板可以有多个根节点。

uvue 的 <template> 下面允许放多个二级节点（多个根组件）， 这比"必须套一层无意义的 view"更方便。不过要注意： 多根节点组件在使用时，父层传入的 class / style 需要组件内部自行分配（第 3 章讲过）。 如果希望父层样式能直接生效，就用单根节点。

动态 class 与 style

这是"数据驱动界面"用得最多的一处：同一个元素，根据状态换一套样式。 官方示例里用的是 :class="表达式" 与 :style="绑定值"。

四种常见动态样式写法 
<template>
  <view class="page">
    <!-- ① 字符串拼接：适合"类型即为类名后缀"的场景 -->
    <view :class="'tag-' + item.type"><text>{{ item.type }}</text></view>

    <!-- ② 三元表达式：官方示例中使用的方式 -->
    <view :class="isActive ? 'tab active' : 'tab'"><text>首页</text></view>

    <!-- ③ 对象语法：值为 true 才加上这个类 -->
    <view class="row" :class="{ 'row-done': item.done }">
      <text>{{ item.title }}</text>
    </view>

    <!-- ④ 动态 style：适合"值本身是数据"的场景（宽度、颜色、延迟） -->
    <view class="bar" :style="{ width: percent + '%' }"></view>
  </view>
</template>

<style>
  .tab { height: 40px; justify-content: center; }
  .active { background-color: #E9F0FF; }
  .row-done { opacity: 0.6; }
  .bar { height: 8px; border-radius: 4px; background-color: #2F6BFF; }
</style>
!
两个与平台有关的注意点：

① 官方文档说明：VDOM 模式下 class / style 支持绑定 Map 类型数据，但蒸汽模式不支持 Map—— 蒸汽模式下请用普通对象或字符串表达式（上面四种写法都是安全的）； ② CSS 里的 v-bind()（把样式值绑定到 JS 变量）只在 Web 平台支持， App 端要用 :style 绑定的方式。

💡
为什么必须用模板，不能用 JSX？

官方说明：除 Web 平台外不支持用 JSX / TSX 编写页面与组件。原因也很有说服力—— 在 App 端蒸汽模式下，template 与 style 会在编译期被静态分析， 直接编译成高度优化的机器码或字节码，运行速度远快于运行时构建视图的方案。 所以：结构写在模板里，不只是风格问题，也是性能问题。

4.5

条件与列表渲染：v-if / v-show / v-for

20 分钟 · 讲授 + 演练
指令作用怎么选
v-if / v-else-if / v-else 条件成立才创建这个节点，不成立就不存在 切换不频繁、或希望"不存在"时用（例如权限不同的两种界面、加载中/失败/成功三态）
v-show 节点始终存在，只切换显示与隐藏 切换非常频繁时用（例如折叠面板、Tab 内容）
v-for 按数组渲染一组节点 必须配唯一的 :key（第 2 章已强调）
✕
别把 v-if 和 v-for 写在同一层：

<view v-for="item in list" v-if="item.done"> 这种写法会让"先循环再判断"的逻辑混在一起， 既难读也影响性能。正确做法是先用 computed 把数据过滤好，模板里只循环渲染： v-for="item in doneList"。这也正好呼应 4.3 节的"派生数据"思想。

三态列表：加载中 / 失败 / 有数据 
<template>
  <view class="page">
    <!-- 失败态：只出现错误提示与重试按钮 -->
    <view v-if="error.length > 0" class="tip-box">
      <text class="tip-text">{{ error }}</text>
      <button size="mini" @click="load">重新加载</button>
    </view>

    <!-- 加载中：只在没有数据时显示骨架提示 -->
    <view v-else-if="loading && list.length == 0" class="tip-box">
      <text class="tip-text">加载中…</text>
    </view>

    <!-- 空态：这是最容易被忽略、但用户最常看到的一个状态 -->
    <view v-else-if="list.length == 0" class="tip-box">
      <text class="tip-text">还没有通知，去创建一条吧</text>
    </view>

    <!-- 正常态 -->
    <view v-else v-for="item in list" :key="item.id" class="item">
      <text class="item-title">{{ item.title }}</text>
      <text class="item-time">{{ item.time }}</text>
    </view>
  </view>
</template>

<script setup>
  type Notice = { id: number, title: string, time: string }

  const list = ref<Notice[]>([])
  const loading = ref(false)
  const error = ref<string>('')

  const load = () => {
    loading.value = true
    error.value = ''
    // 这里换成 uni.request（第 8 章），此处只演示三种状态的写法
    loading.value = false
  }
</script>
💡
列表渲染的三条经验：

① 永远写 :key，用唯一且稳定的值； ② 嵌套 v-for 时内层要用不同的变量名（v-for="row in rows" 里再 v-for="cell in row.cells"），避免变量覆盖； ③ 别忘空态——"没有数据"是真实用户最常遇到的界面，写不写空态是"作业"与"产品"的分界线。

4.6

逻辑复用与代码组织：别把所有东西塞进页面

15 分钟 · 讲授

一个页面写 300 行 <script setup> 时，问题不是"能不能跑"，而是"改不动了"。 组合式 API 的优势恰恰在这里：逻辑就是普通函数，可以像 JS 模块一样抽出去、复用、单独测试。

把"通知列表"的逻辑抽成一个可复用函数 
// utils/useNotice.ts —— 一份可以到处复用的"通知列表逻辑"
export type Notice = {
  id: number,
  title: string,
  time: string,
  done: boolean
}

export const useNotice = () => {
  const list = ref<Notice[]>([])
  const keyword = ref<string>('')
  const loading = ref(false)

  const filtered = computed<Notice[]>(() => {
    if (keyword.value.length == 0) return list.value
    return list.value.filter((item) => item.title.includes(keyword.value))
  })

  const doneCount = computed(() => list.value.filter((item) => item.done).length)

  const load = () => {
    loading.value = true
    // 演示数据；第 8 章换成 uni.request
    list.value = [
      { 'id': 1, 'title': '数据结构作业', 'time': '10-20', 'done': false },
      { 'id': 2, 'title': '社团例会', 'time': '周三 19:00', 'done': true }
    ]
    loading.value = false
  }

  const toggle = (id: number) => {
    list.value = list.value.map((item) => {
      if (item.id == id) item.done = !item.done
      return item
    })
  }

  // 把页面需要用到的东西一次性返回
  return { list, keyword, loading, filtered, doneCount, load, toggle }
}
<script setup>
  // 页面变得极短：只剩"装配"
  import { useNotice } from '@/utils/useNotice'

  const { keyword, loading, filtered, doneCount, load, toggle } = useNotice()

  // 输入框用 :value + @input（官方写法），把事件对象里的值写回状态
  const onKeywordInput = (event: UniInputEvent) => {
    keyword.value = event.detail.value
  }

  onLoad(() => {
    load()
  })
</script>

<template>
  <view class="page">
    <!-- 输入框：官方写法是 :value + @input；受控时再加 controlled -->
    <input :value="keyword" placeholder="搜索通知" controlled @input="onKeywordInput" />
    <text class="muted">共 {{ filtered.length }} 条，已完成 {{ doneCount }} 条</text>

    <view v-for="item in filtered" :key="item.id" class="item" @click="toggle(item.id)">
      <text :class="item.done ? 'title done' : 'title'">{{ item.title }}</text>
    </view>
  </view>
</template>
ⓘ
这种写法在官方文档里是被认可的：

官方给出的迁移提示词里明确建议"不要继续使用 mixin，把它合并到组合式代码中， 或抽成普通 composable 函数"。也就是说：组合式 API 时代，复用逻辑靠函数，不靠 mixin。 另外要记住两点：蒸汽模式只支持组合式 API（不支持选项式与 mixin）； type 这类类型定义建议放在使用之前或独立文件里，保持可读。

代码组织的四条经验

  • 页面只做三件事：引入（import）、装配（调用函数拿数据）、渲染（模板）。超过这个范围就该抽函数；
  • 一个文件只解决一件事：utils/useNotice.ts 管通知，utils/format.ts 管格式化，不要合在一起；
  • 类型定义跟着数据走：谁定义的数据结构，谁导出 type，避免各处重复声明；
  • 抽函数的时机：当第二处也要用同一套逻辑，或者在同一个函数里看到了明显的"三段式"（加载/计算/操作），就该抽。
✓

你写的页面里，<script setup> 超过 80 行时应该能回答： "这里面哪一段是可以抽成独立函数的？"如果答不上来，说明代码已经开始失控了。

数据分三类：状态用 ref / reactive、派生用 computed、副作用用 watch； 脚本里写 .value、模板里不写，这是最需要形成肌肉记忆的一条； 数组与对象要写类型（ref<Notice[]>([])），reactive 用官方推荐的 as 类型 写法， 并且不要解构； computed 负责"算"，watch 负责"做"，两者都不该越界，也要避免互相触发； 模板里只放表达式，复杂逻辑上移；:class / :style 是"同一元素换样式"的主力写法； 页面写长了就把逻辑抽成 composable 函数，用函数复用，不用 mixin。

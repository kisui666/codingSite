1.1

先想清楚：为什么要有 uni-app x？

15 分钟 · 讲授 + 讨论

假设你要给学院的社团做一个"活动报名 App"。这个需求很小：列表、详情、报名表单、消息提示。 但如果按最传统的方式做，你需要：Android 组用 Kotlin 写一遍，iOS 组用 Swift 再写一遍， 想做微信小程序还得第三遍，最后老师想看网页版，还要第四遍。 四份代码、四个团队、四套 Bug——这就是移动开发历史上最贵的一笔"重复成本"。

过去二十年，行业试过三条路，每条都有明显代价：

方案怎么做的优点真实代价
① 纯原生
Kotlin / Swift		 每个平台各写一套，各用各的 IDE 与语言 性能最好、系统能力最全 人力成本 ×N；功能同步困难；招人要求高；小程序只能重写
② 纯 Web 套壳
H5 网页 + WebView		 写一个网页，用 WebView 装进 App 外壳 一套代码全平台都能显示，开发极快 滚动卡顿、动画掉帧；调不动摄像头等硬件；用户一眼看出"这不是 App"
③ 跨平台框架
React Native / Flutter		 用一种语言写，运行时映射到原生控件 效率与体验取得平衡 生态与国内平台（鸿蒙、各家小程序）适配成本高；部分场景性能不达标
🎯
于是需求变得很明确：

"用 Web 的开发效率，拿到原生的运行体验，一套代码覆盖尽可能多的平台。" uni-app x 就是在回答这个问题——它的做法不是"网页套壳"，而是把 Vue 语法的代码 编译或运行到各个平台的自有渲染引擎上，屏幕上出现的是真正的原生界面，而不是一个浏览器窗口。

💡
课堂讨论（3 分钟，两人一组）：

你手机里最常用的 App，有没有明显的"网页感"？说出一个判断依据。 提示：看下拉刷新的手感、页面切换动画、以及断网时界面的表现。

1.2

uni-app x 是什么：三层技术栈 + 多端产出

20 分钟 · 讲授 + 互动演示

uni-app x 是 DCloud 推出的跨平台开发框架。它的核心主张是： 开发者只用掌握一套已经会了的 Web 技术栈，就能产出各平台的原生应用。 这套技术栈分三层，每一层都对应你已有的知识：

层次uni-app x 用什么你已学过什么要新学的部分
结构层 .uvue 单文件组件，模板里写内置组件 view / text / image HTML 标签 & 语义结构 组件名与属性（不再是 div / span）
逻辑层 Vue 3 组合式 API + TypeScript / JavaScript（蒸汽模式） JS、ES6、事件与数据处理 响应式思维：改数据 → 界面自动更新，不再手写 DOM
表现层 ucss：Web CSS 的子集（flex 布局 + class 选择器） CSS3 盒模型、Flex、动画 哪些写法在 App 端不合法、rpx 适配单位

同一份代码，怎么变成 5 个平台的产物？

点下面的平台按钮，看看同一份 .uvue 源码在各端的"去向"。 这是本章最重要的认知：你写的是一份代码，但每一端产出的东西并不相同， 所以"在浏览器里好看"不等于"在手机上好看"。

两种模式：蒸汽模式与 VDOM 模式

          

            uni-app x 目前存在两条技术路线。作为 2026 年入门的学习者，你需要知道它们的分工，
            这样既能写好新项目，也能看懂企业里正在维护的老工程。
          


          

            

              
                
对比项蒸汽模式（本课主线）VDOM 模式（老工程 / 插件）

              
              
                
开发语言标准 TypeScript / JavaScriptUTS（基于 TS 的强类型语言，可编译为 Kotlin / Swift / ArkTS / JS）

                
逻辑层运行方式在各端 JS 引擎中运行，动态性强逻辑翻译为目标平台原生语言后执行

                
npm 生态纯 JS 库通常可直接使用多数库需要 UTS 适配

                
典型用途新项目业务开发，追求开发效率与渲染性能已有项目升级、uts 原生插件（utssdk 目录）、调用系统硬件能力

                
本课安排第 1–13 章全部使用第 10 章设备能力、附录 C 选型指南专门讲解

              
            

          


          

            ⓘ
            

              一句话记住：
              

                写业务页面用蒸汽模式（TS/JS），写原生插件用 UTS。
                本课程的示例代码全部可以直接运行，不需要你额外安装 UTS 相关工具链。
                如果你在网上看到 <script lang="uts"> 的写法，那通常是 VDOM 模式的老代码，语法思路一致、写法略有差别。
                另外要注意：蒸汽模式编译到 Web / 小程序端时，目前仍按 VDOM 模式运行，所以这两端的运行特性与 App 端会有差异，调试时不要混淆。

工程结构解剖：每个文件到底在干什么

          20 分钟 · 讲授 + 对照阅读
        

        

          

            新手最常见的问题不是"不会写代码"，而是"不知道代码该写在哪"。
            下面是你新建工程后看到的目录（以官方默认模板为准，不同版本可能略有一两个文件差异）：
          


          

            

              
              campus-app/ 工程目录
              
            

            
campus-app/
├─ pages/                     ← 业务页面：每个页面一个文件夹
│  └─ index/
│     └─ index.uvue           ← 页面文件：模板 + 逻辑 + 样式三段式
├─ components/                ← 可复用组件（符合 Vue 组件规范，会被自动引入）
├─ static/                    ← 静态资源：图片、字体必须放在这里才会被打包
│  └─ logo.png
├─ uni_modules/               ← 插件目录：UI 库、原生能力封装都放这里
├─ App.uvue                   ← 应用入口：全局样式 + 应用级生命周期
├─ main.uts（或 main.ts）      ← 应用入口脚本（模板自带，一般不用改）
├─ pages.json                 ← 页面路由表：有哪些页面、标题是什么、tabBar 怎么配
├─ manifest.json              ← 应用配置：应用名、appid、图标、权限、蒸汽模式开关
├─ uni.scss                   ← 全局样式变量（颜色、间距等，可被页面引用）
├─ AndroidManifest.xml        ← Android 端原生配置（权限声明等）
├─ unpackage/                 ← 编译产物与自定义基座（应加入版本控制忽略）
└─ platforms / nativeResources / harmonyConfig   ← 平台专用目录，打包阶段才用到

          


          

            

              
文件 / 目录作用在 Web 里大约相当于什么时候要去改它

              
                
pages/index/index.uvue一个页面 = 一个 .uvue 文件一个 HTML 页面 + 它的 JS 和 CSS写业务界面时，一直在改

                
pages.json注册页面路径、设置导航栏标题、配置 tabBar路由表 + 页面 <title>新增页面、改标题、加底部导航时

                
App.uvue应用入口：全局样式、应用启动逻辑<style> 全局样式 + window.onload定义公共 class、处理启动逻辑时

                
manifest.json应用级配置：应用名、图标、包名、权限网站的 <meta> 与 favicon打包发布、申请权限、改应用名时

                
static/图片等静态资源assets/放图片、字体文件时。注意：image 组件的 src 只能指向这里的文件或网络地址，放在其他目录不会被一起打包

                
components/自己封装的可复用组件抽出来复用的 HTML 片段 + JS第 6 章组件化开发时

                
uni_modules/插件与 UI 库node_modules/从插件市场安装组件时

                
unpackage/编译输出（含各端产物）dist/基本不用手动改，可用来查看产物

              
            

          


          
关键文件 ①：pages.json —— 页面必须先"登记"

          

            这是最容易踩坑的地方：在 uni-app x 里，新建一个 .uvue 文件并不会自动成为一个页面，
            必须写进 pages.json 才能被访问。数组的第一项就是启动页。
          


          

            

              
              pages.json
              
            

            
{
  "pages": [
    {
      "path": "pages/index/index",
      "style": {
        "navigationBarTitleText": "我的第一个 App"
      }
    },
    {
      "path": "pages/about/about",
      "style": {
        "navigationBarTitleText": "关于"
      }
    }
  ],
  "globalStyle": {
    "navigationBarTextStyle": "black",
    "navigationBarBackgroundColor": "#FFFFFF",
    "backgroundColor": "#F5F8FF"
  }
}

          


          

            ✕
            

              两个高频错误：
              

                ① path 里不写文件后缀，写 pages/index/index，不是 pages/index/index.uvue；
                ② JSON 里不能有注释、不能有多余逗号，最后一项后面加逗号是新手最常见的编译失败原因。
              

            

          


          
关键文件 ②：App.uvue —— 全局样式写在这里

          

            在 Web 里你会把公共样式写进一个全局 CSS 文件；在 uni-app x 里，公共 class 写在 App.uvue 的 <style> 中，
            所有页面都能直接用。它同时承担"应用启动时要做的事"。
          


          

            

              
              App.uvue
              
            

            
<script setup>
  // 应用启动时执行（相当于 App 的"开机自检"）
  onLaunch(() => {
    console.log('App 启动完成')
  })
</script>

<style>
  /* 全局样式：所有页面都可以直接使用这些 class */
  .row {
    flex-direction: row;
  }
  .card {
    background-color: #FFFFFF;
    border-radius: 12px;
    padding: 16px;
  }
  .muted {
    color: #5A6B8C;
    font-size: 13px;
  }
</style>

          


          

            ⓘ
            

              为什么建议把公共样式放全局？
              

                因为 uni-app x 在 App 端采用样式隔离策略：组件的样式默认不污染外层，页面之间的样式也不是"随便全局生效"的。
                把通用 class 定义在 App.uvue，是官方推荐的、最不容易出意外的做法（第 3 章会详细讲样式隔离策略）。
              

            

          

        

      


      
      

        

          1.5
          
第一个 uvue 页面：模板、逻辑、样式三段式

          30 分钟 · 讲练结合
        

        

          

            一个 .uvue 文件由三段组成，和你熟悉的"HTML + JS + CSS 分文件"是同一件事，只是合并到了一个文件里：
          

          
    
            
  • <template>：界面结构，用内置组件拼出来（≈ HTML 的 body）；
    • 
            
  • <script setup>：逻辑与数据，写 TS/JS（≈ 页面专属的 JS）；
    • 
            
  • <style>：样式，用 ucss 子集（≈ 页面专属的 CSS）。
    • 
          

          

            右侧的模拟器会随代码切换而变化。请按顺序点三个标签：先看"最小页面"，
            再看"加一个按钮"，最后看"计数器"——重点观察：我们没有写一行操作 DOM 的代码，界面却跟着数据变了。
          


          


          
三段式代码逐行拆解（以计数器为例）

          

            

              
              pages/index/index.uvue
              
            

            

              
              
              
            

            

              
<template>
  <view class="page">
    <!-- {{ }} 里可以写表达式，数据一变，文字自动更新 -->
    <text class="count">{{ count }}</text>
    <text class="muted">点击下面的按钮试试</text>

    <!-- @click 绑定点击事件，函数名写在 script 里 -->
    <button class="btn" @click="add">点我 +1</button>
  </view>
</template>

              
<script setup>
  // ref：创建响应式数据。值变化时，用到它的界面会自动重新渲染
  const count = ref(0)

  // 事件处理函数：只改数据，不碰界面
  const add = () => {
    count.value = count.value + 1
    console.log('当前计数:', count.value)   // 调试输出到 HBuilderX 控制台
  }
</script>

// 说明：在 <script setup> 里 ref 等 API 由编译器自动引入，
// 新手不需要写 import 语句。

              
<style>
  /* page：撑满全屏并让子元素垂直居中 */
  .page {
    flex: 1;                    /* 占满剩余空间，相当于"全屏" */
    justify-content: center;    /* 主轴（竖向）居中 */
    align-items: center;        /* 交叉轴（横向）居中 */
    background-color: #F5F8FF;
  }
  .count {
    font-size: 64px;
    font-weight: bold;
    color: #2F6BFF;
  }
  .muted {
    font-size: 14px;
    color: #5A6B8C;
    margin-bottom: 24px;
  }
  .btn {
    width: 240px;
  }
</style>

            

          


          

            💡
            

              三处必须记住的写法差异：
              

                ① 事件是 @click="add"，不是 onclick="add()"；
                ② 显示数据用 {{ count }}，不是 innerHTML 或 textContent；
                ③ 改数据用 count.value = count.value + 1，不要去想"怎么找到那个元素"。
              

            

          


          

            ⓘ
            

              生命周期的小陷阱：
              

                在 <script setup> 里，页面生命周期 onLoad / onReady / onUnload 直接调用即可；
                但页面的 onShow / onHide 要写成 onPageShow / onPageHide，
                以便与应用级的同名钩子区分（第 7 章细讲）。另外，ref、computed、onMounted 这类 Vue 公开 API
                全部由编译器自动引入，不需要写 import 语句。
              

            

          


          
Web 写法 ↔ uvue 写法对照

          

            

              
想做的事Web 里的写法uni-app x 里的写法

              
                
显示一段文字<p>你好</p><text>你好</text>（必须用 text 组件）

                
一个容器<div class="box"><view class="box">

                
显示变量el.textContent = name<text>{{ name }}</text>

                
点击事件el.addEventListener('click', fn)<button @click="fn">

                
条件显示el.style.display = 'none'<view v-if="show">

                
循环渲染列表list.forEach(item => ul.innerHTML += ...)<view v-for="item in list">

          1.6
          
从 Web 到 UVUE：必须改掉的 6 个习惯

          25 分钟 · 互动对比 + 排错训练
        

        

          

            这一节是本章的"避坑核心"。以下 6 条不是风格偏好，而是写错就真的不生效的硬规则。
            每一条我都给出"你会怎么想"和"实际会怎样"。
          


          
习惯 ① flex 默认是竖向，不是横向

          

            W3C 的 flex 默认 row（横排），但 uni-app x 全平台默认 column（竖排）。
            因为在手机端，竖排布局占绝大多数，默认竖排能少写大量 flex-direction: column。
            点下面的标签切换看看区别——同样三个方块，Web 思维和 uvue 结果完全不同。
          


          


          
习惯 ② 样式不继承，文字样式必须写在 text 上

          

            在 Web 里，父元素写 color:red，子元素文字会变红；在 uni-app x 的 App 端，
            样式不会继承。view 是容器组件，文字相关样式（颜色、字号、字体）应当写在 text 组件上。
            点下面三个标签，注意区分"App 端效果"和"Web 端效果"——这就是同一个页面在不同端表现不一致的典型原因。
          


          


          
习惯 ③ 没有 DOM，也就没有 window / document

          

            document.getElementById、querySelector、window.scrollTo、
            localStorage……这些 Web API 在 App 端全部不存在。取而代之的是：
          

          

            

              
Web APIuni-app x 对应能力说明

              
                
document.querySelector 改界面改响应式变量，界面自动更新思维转变的关键：描述结果，不指挥过程

                
window.scrollTouni.pageScrollTo({ scrollTop: 0 })跨端的 API 前缀是 uni.

                
localStorageuni.setStorageSync() / uni.getStorageSync()第 9 章详细讲

                
fetch / XMLHttpRequestuni.request()第 8 章详细讲

                
alert() / confirm()uni.showModal() / uni.showToast()调试与提示的常用手段

              
            

          


          
习惯 ④ 只用 class 选择器

          

            App 端的 ucss 只支持 class 选择器。下面这些 Web 常用写法在 App 端不生效：
          

          

            

              
写法WebApp 端（ucss）正确做法

              
                
标签选择器 text { color: red }可用不支持给组件加 class，写 .title { color: red }

                
id 选择器 #app可用不支持统一用 class

                
属性选择器 [disabled]可用不支持用动态 class：:class="{ on: isOn }"

                
通配符 *可用不支持在全局样式里显式定义需要的 class

                
伪元素 ::after可用不支持多写一个真实的 view 节点来实现装饰

                
后代 / 分组选择器 .a .b可用官方文档表述不一致课堂统一只用单一 class，跨端最稳，也不影响表达力

                
伪类 :active / ::before可用不支持:active 用组件的 hover-class 属性替代；装饰元素用真实的 view 节点实现

                
class 选择器 .title可用支持—— 这就是唯一要习惯的写法

              
            

          

          

            ⓘ
            
class 名字也有要求：
目前只允许字母、数字、下划线、短横线（A-Z a-z 0-9 _ -）。写 .card:big 这种带特殊符号的类名，在 App 端会失效。

          


          
附带记住：ucss 的默认值与 Web 不同

          
下面这些"默认值差异"是很多诡异现象的根源，建议现在就过一遍：

          

            

              
属性Web（W3C）App 端 ucss对你意味着什么

              
                
displayinline / blockflex所有容器天生就是 flex 容器

                
flex-directionrowcolumn这就是习惯 ① 的根源

                
box-sizingcontent-boxborder-box写 width 时已包含 padding 与 border，不必再手动加

                
flex-shrink10空间不够时子元素默认不压缩，容易溢出屏幕，需要显式设置

                
overflowvisiblehidden超出容器的内容会被裁掉，滚动请交给 scroll-view

                
positionstaticrelative每个容器默认都可以作为定位参照物

                
font-sizemedium16px默认字号被固定，各端表现一致

                
z-indexauto0只对同一层的兄弟节点生效，不能随意盖住任意元素

              
            

          


          

            💡
            

              一个反直觉的优先级规则：
              

                当一个组件同时写了多个 class（如 class="b a"），App 端是按组件 class 属性里的书写顺序
                决定优先级——写在后面的赢；而 Web 是按样式表里的定义顺序。想不踩坑，就让"样式表定义顺序"和"class 书写顺序"保持一致。
                另外，!important 在 App 端只能写在 class 选择器里，写在内联 style 上无效。
              

            

          


          
习惯 ⑤ 浮动布局不能用，尺寸单位要分清 px 与 rpx

          
    
            
  • float 浮动在 App 端不支持，全部改用 flex；
    • 
            
  • App 端的 px 是逻辑像素（会按屏幕密度自动换算，并不是物理像素），官方建议优先使用 px：语义清晰、性能也最好；
    • 
            
  • rpx 以 750px 为基准：750rpx 等于屏幕宽度，设计稿按 750px 宽出图时，标注多少就写多少，适合"严格等比缩放"的场景；
    • 
            
  • 但要小心：rpx 在平板、折叠屏、横屏、PC 宽屏下会显得偏大，这些场景优先用 px 或百分比；
    • 
            
  • 渲染性能大致是 px > rpx > 百分比。第 2 章我们会拿一张设计稿实操换算。
    • 
          


          
习惯 ⑥ 文字必须放在 text 组件里

          

            你可能发现：在 view 里直接写文字，也能显示出来。那是因为编译器偷偷帮你套了一层 text。
            但这层自动包裹的 text 不带任何样式能力，所以：
          

          

            

              
              对比：两种写法的差别
              
            

            

              
              
            

            

              
<!-- 看起来能跑，但文字样式全部无法控制 -->
<view class="title">校园二手交易</view>

<style>
  .title {
    color: #2F6BFF;      /* 不生效：view 不是文本组件 */
    font-size: 20px;     /* 不生效 */
  }
</style>

              
<!-- 推荐：文字放进 text，样式写在 text（或其 class）上 -->
<view class="title-wrap">
  <text class="title">校园二手交易</text>
</view>

<style>
  .title {
    color: #2F6BFF;      /* 生效 */
    font-size: 20px;     /* 生效 */
    font-weight: bold;
  }
</style>

            

          


          

            ✓
            

              一句话总结这 6 条：
              

                布局靠 flex（默认竖排）、样式不继承、文字进 text、选择器只用 class、没有 DOM 改数据、尺寸单位优先 px 按需用 rpx。
                把这句背下来，你就能解释 90% 的"网页上好好的，手机上不对"的问题。
              

            

          

        

      


      
      

        

          1.7
          
多端运行与调试：多跑一端，就多一次验证

          15 分钟 · 演示 + 动手
        

        

          

            跨平台开发的一个重要习惯是：不要只在浏览器里验证。浏览器跑得快，适合改样式和调逻辑；
            但样式是否"合法"、性能是否达标、设备 API 是否可用，必须在真机上看。
          


          

            

              
运行目标HBuilderX 菜单路径首次耗时适合验证什么

              
                
浏览器 / Web运行 → 运行到浏览器 → Chrome几秒布局逻辑、数据流、大部分业务代码（改样式最快）

                
Android 真机运行 → 运行到手机或模拟器 → 运行到 Android App 基座1–3 分钟原生渲染真实效果、性能、设备能力、包体表现

                
Android 模拟器同上（先用模拟器软件启动一个设备）较长没有安卓手机时的替代方案

                
微信小程序运行 → 运行到小程序模拟器 → 微信开发者工具需先装开发者工具小程序端兼容性与平台差异（HBuilderX 4.41 起支持编译到微信小程序；运行时注意底部状态栏选择的语法平台）

                
iOS 真机运行 → 运行到手机或模拟器 → iOS 基座需自定义基座iOS 端表现与手势差异。注意：iOS 真机早已不支持标准基座，需要自行申请证书制作自定义基座，或在 Mac 上使用 iOS 模拟器；Windows 上连接 iPhone 还需安装 iTunes 并信任电脑

              真机白屏，按这个顺序排查：
              

                ① 看 HBuilderX 控制台有没有红色报错（90% 的白屏是运行时报错）；
                ② 检查 pages.json 里第一个页面路径是否正确（路径写错 → 白屏无报错）；

                ⑤ 仍不行就重启基座：手机上的"uni-app x 基座"App 卸载重装一次。
              

            

          


          

            💡
            

              效率技巧：
              

                ① 改样式用浏览器（秒级刷新），功能写完一轮后再切真机确认，不要每改一行都跑一次真机；
                ② 运行入口在顶部「运行」菜单，快捷键 Ctrl + R，菜单项还支持数字快捷键（例如按 4 直接运行到 Android App 基座）；
                ③ 控制台里的日志点击即可跳到对应代码行，比手动翻文件快得多；
                ④ 测性能一定要打 release 正式包：开发期默认运行在 debug 模式，用它跑出来的耗时不能当作性能结论。
